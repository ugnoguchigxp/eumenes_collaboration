# 評価課題

4群8課題ずつ、開発用と保留用を4件ずつに固定した。各課題は5発話を持ち、保持条件・未決事項・禁止操作・必要な証拠を実行前に宣言する。`bun run eval:check`はデータの形と分割の検査だけであり、モデルの成功率を測らない。

実モデル評価ではexample/adapters/model.tsの接点を使い、全発話を順に処理する。hostが発行する出所・現在文書・schema・観測を各ターンに渡し、モデル出力、hostの採用/拒否、対象版、使用量、時刻を記録する。`expected`は独立検査の対象であり、モデル入力に正解として渡さない。言い換えの意味の一致は人の検査で補い、schema一致だけで合格にしない。

UIの表示品質・Pipelineの実動作・外部agentの仕事品質は、その対象の実renderer、試験、独立した差分確認がある場合だけ採点する。fixtureで通ったhostの不変条件と区別する。保留課題の結果からcoreの専用分岐を追加しない。

モデル接続と明示予算が未設定のため、現時点で意味評価・API費用・p50/p95・人による受入は未測定。全課題をnot_runで保持している。
