# 先回り支援の比較評価

対象と工程は[実装計画](../../spec/proactive-collaboration-implementation-2026-11-11.md)に従う。現在は、同じ開発用6課題で現行方式Aの通常返答の見直しを検証する。以下にA+（補足欄）と背景準備の先行比較、および保留中の正式比較の登録案も記録している。

## 課題と採点

`development.json` は調整用6件、`holdout.json` は評価用24件。評価用は、準備が役立つ、阻害要因がある、待つのが妥当、提案不要を各6件とする。課題の `opening` と `update` を順に送る。`criteria` と `followUp` は採点者・利用者役の資料とし、制作担当の入力には含めない。

1. 各発言の確定後に、会話のメッセージ、作品定義と版、条件と出所参照を、試験用会話のAPIから記録する。結果が未確定の発言は状態を照会し、別の依頼として再送しない。
2. `update` の確定後から、同じ観測時間内で通常返答、補足、自発提案を採点する。初期案は30秒。利用者役は、採点条件で求める判断材料が得られなかった場合だけ `followUp` を一度送る。`followUp` がない課題では待機または終了する。訂正や切替を予定した発言は追加指示の件数から除く。
3. 成果物と条件が一致したか、既出条件の言い直し・追加指示が何件あったか、余分にやり直した工程が何件あったかを記録する。不要な提案は内容と時期を採点し、失効した結果の提示・禁止中の割り込み・重複配送などの違反と別に数える。比較の前に許容する時間帯を固定する。
4. 構成名を伏せて、同じ資料を使い同じ基準で採点する。各試行の状態は `completed`、`incomplete`、`failed` のいずれか。失敗や未完了も分母に含める。前景の時間は発言受付から返答の確定までを記録し、測れなかった場合は空配列にする。

## ローカルの検査と集計

```sh
bun eval/proactive/index.ts
bun test ./test/proactive-eval.test.ts ./test/proactive-observation.test.ts
bun eval/proactive/index.ts --scores /path/to/scored-runs.json --modes A,A+,B,C --split holdout
```

課題検査は分割、重複ID、観測後の追加指示があるべき課題を確認し、課題とprotocolのSHA-256を出す。集計は一試行につき `taskId`、`mode`、`repetition`、`status`、`conditionsMet`、`followUps`、`rework`、`unnecessaryProposals`、`boundaryViolations`、`foregroundMs` を持つJSON配列を読む。指定した全モードで同じ課題と反復が揃っている場合だけ集計する。集計結果には各試行の成否を残し、課題単位の改善、反復間の揺れ、不要な提案の内訳を確認できる。

## 基準の状態

2026年11月11日。固定応答を使う本体の試験で、通常のUI共同制作から作品と条件の状態を読み出し、部分訂正後に未変更条件と出所が保たれることを確認した。本体の試験用モデルに、既存の状態欄を付けるヘルパーを接続した。変更は試験内に限る。

`protocol.json` は正式比較の登録案。単一経路・各構成2反復、Agencyは全構成でF、追加API費用は0 USDとする。呼出し上限は従来のAで48試行に161回使った記録を基に、AとA+に各220回、BとCに各320回を置く。B・Cには背景推論の余裕を含む。前景p95の許容値はA比10%以内かつ1,000 ms以内。比較を開始する前に各構成の実装版、実際の前景・背景経路とAgency設定、課題と実行コードのハッシュ、利用者役・採点表・人の通し試験を一つの登録にまとめる。 [実装計画の登録条件](../../spec/proactive-collaboration-implementation-2026-11-11.md#正式比較の登録)

初回の現行方式Aの試行は、専用の登録条件で48試行を採取した。モデル経路・予算・結果とSteerの確認は[隔離試験の記録](../results/2026-11-11/proactive-mode-a/README.md)にある。人による採点と、A+・B・Cの比較は後続工程で扱う。

## 開発用の候補確認と観測

開発用6件について、実モデルが作成・更新した作品と条件を固定し、現行定義だけを読む場合と更新前の定義も読む場合で、次の一手と保留の判断を比較した。結果と再現手順は[開発用の検証記録](../results/2026-11-12/proactive-ui-development/README.md)にある。

正式比較の試験コードでは、通常返答の確定後に、そのメッセージIDを起点とする。30秒の観測枠の終わりか、利用者役の追加発言の直前に `readConversation` で会話を読み、`observeConversation` と `decisionTranscript` で利用者役と採点者に同じ文面・順序・相対時刻を渡す。この時点の記録を固定する。試行終了時にも読み直し、判断後に届いた単独メッセージを別に残す。会話本文への表示を対象とし、成果物専用メッセージは除く。実際の画面表示や音声の再生は通し試験で別に照合する。 [観測コード](observation.ts)

開発用の固定試験は、通常返答とは別のメッセージを隔離ホストの会話に保存し、実際の会話APIから取り出して、利用者役・採点者・集計が同じ内容を使うところまで確認する。先の基準測定と同じEumenesコミットを展開し、固定依存を導入したディレクトリを指定する。

```sh
PROACTIVE_EUMENES_SOURCE=/absolute/path/to/isolated-eumenes \
  bun test ./test/proactive-observation.test.ts ./test/proactive-eval.test.ts
```

## 開発用のA+と背景準備の比較

A+の試験では、隔離ホストの更新ターンの既存出力契約に補足欄を追加する。通常返答と同じモデル呼出しから得た補足を、対応する返答が保存されたことを確かめた後で試験会話に添える。その試行で確定した作品と条件を、そのまま背景準備の入力に使う。各課題で、通常本文とA+の補足の両方に現れなかった具体的な根拠・確認結果を、作品と条件から検証できた場合に一件と数える。両方の補足は300字まで。開発用6件のうち3課題以上が工程3へ進む条件となる。 [実装計画の採否](../../spec/proactive-collaboration-implementation-2026-11-11.md#採否)

```sh
bun eval/proactive/supplement-trial.mjs <隔離Eumenes> <新規A+出力.jsonl>
bun eval/proactive/development.mjs <隔離Eumenes> <A+出力.jsonl> <新規背景準備出力.jsonl> --current
```

開発用6件で追加の根拠・確認結果が得られたのは2課題だった。工程3への移行は見送る。 [A+と背景準備の比較結果](../results/2026-11-12/proactive-ui-a-plus/README.md)

## 開発用の現行方式AとA+の比較

開発用6件をAとA+で各2反復する。先行試験の初稿・初回返答・出所付き条件を隔離ホストで再生する。出所を初回の利用者発言に結び直し、作品定義と条件が保管済みの内容と一致したことを確認してから、更新を実モデルに渡す。両方式で同じ30秒の観測枠を使う。利用者役には方式名を渡さず、会話で届いた文面と作品から判断材料の不足を確認する。追加質問が必要と判定した場合は、課題で定めた質問を一度だけ実際に送る。

改善は、完成と条件充足を保って追加質問か実際の手戻りが減った場合に数える。提案が具体的になっても、既に答えたことの繰り返しや、追加質問・手戻りに差がない場合は、主指標の改善と分けて記録する。

```sh
bun eval/proactive/compare-supplement.mjs <隔離Eumenes> <先行A+出力.jsonl.gz> <新規固定出力.jsonl> --fixed
bun eval/proactive/compare-supplement.mjs <隔離Eumenes> <先行A+出力.jsonl.gz> <新規比較出力.jsonl>
```

開発用6件の比較で追加質問は4回から2回に減った。差が出た2課題では両方式で同等の判断材料が得られ、補足は表示されなかった。提案不要の課題でA+の1反復が未完了だったため、A+単独で進める判断は見送る。 [現行方式AとA+の比較結果](../results/2026-11-12/proactive-ui-a-vs-plus/README.md)

## 開発用の通常返答の見直し

先行比較のAを基準とし、同じ初稿を再生する。同じ隔離ホストの別コピーに、`bun run context:build` で生成したCollaborationカタログを反映する。実行時に通常ターンの指示に変更した本文が含まれることを確認する。採点観点と利用者役は先行比較と同じものを使う。追加質問の差を判断する際は、通常返答と作品に確認事項や選択肢の実質的な差があるかを直接照合する。待機と完了の課題は全反復で作品の変更箇所と実際の返答を確認する。

```sh
bun eval/proactive/compare-supplement.mjs <見直し後の隔離Eumenes> <先行A+出力.jsonl.gz> <新規固定出力.jsonl> --fixed --only-a
bun eval/proactive/compare-supplement.mjs <見直し後の隔離Eumenes> <先行A+出力.jsonl.gz> <新規比較出力.jsonl> --only-a
```

再試験では追加質問が4回から3回になり、待機と完成の両課題で各2反復の指示を守った。 [通常返答の比較結果](../results/2026-11-12/proactive-ui-a-reply/README.md)

未確認の手順と確認待ちの扱いを見直し、同じ6課題・各2反復で前回のAと比較した。残した指示では追加質問は3回から2回。町内会で代替の受付方法を通常返答の時点で示す課題が残った。 [未確認の手順と確認待ちの比較結果](../results/2026-11-12/proactive-ui-a-confirm/README.md)

代替手段とその実施条件を通常返答で示す指示を試した。残した指示では町内会の1/2反復で最初の返答に代替案があり、追加質問は全体で2回から1回になった。 [代替手段の比較結果](../results/2026-11-12/proactive-ui-a-alternative/README.md)

判断に必要な材料が揃っている場合と、当初の手段が使えない場合を区別した。残した指示では町内会の両反復で代替案とその実施条件が最初の返答にあり、社食の不要な提案と全体の追加質問は0回だった。 [判断材料と代替手段の比較結果](../results/2026-11-12/proactive-ui-a-decision/README.md)

## 評価用24件での変更前後のAの比較

共通指示を固定し、評価用24件で変更前後のAを各2反復した。代替案とその条件は最初の返答で増えた。追加質問は両方式とも14回、不要な提案は2件から13件に増え、採用を見送った。 [事前登録・原記録・採否](../results/2026-11-12/proactive-ui-a-holdout/README.md)

## 代替案を現在の依頼が止まる場合に絞った比較
