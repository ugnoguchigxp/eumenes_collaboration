# Pipeline共同制作で訂正後の最新版を提示する実装計画

2026年11月12日

既存の `collaboration.pipeline` で、下書きを評価している間にユーザーが条件を訂正できるようにする。訂正された条件を出所付きで採用し、必要な箇所を修正して保存する。旧版の評価は現在の判断に使えなくなり、モデルが最新版の評価を選んだ場合は、その版と確認結果を会話と既存の作品画面で受け取れる。最初の受入は隔離EumenesのPipelineで行う。 [先回り支援の実装計画](proactive-collaboration-implementation-2026-11-11.md)

## 1. ユーザーが通る流れ

1. ユーザーが「20秒のタイマー手順を作ってください。実行前に担当者が画面で確認できる形にしてください」と依頼する。担当が初稿を保存し、独立照合に価値があると判断した場合は、自分で現行版に対する評価を依頼する。初回の返信では、保存済みの下書きと評価中の状態を伝えられる。
2. 評価の実行中にユーザーが「時間だけ35秒にしてください」と訂正する。Dialogueが新しい発言を根拠に時間条件を置き換え、画面確認の条件を保つ。担当は最新の `baseRevision` で影響箇所を部分編集し、保存結果から新しい版を取得する。
3. 訂正前の評価結果は、遅れて届いても現在の作品に反映されない。担当が新しい版の評価を自発選択したときは、その版と確定条件を対象にQuickを開始する。追加の判断がユーザーにしかできないときは一問に絞り、回答に依存しない下書き作業を進める。
4. 最終提示では「35秒に変更した下書き」と、同じ版で確認できた範囲や残った指摘を伝える。評価を選ばなかった場合や確認が終わらなかった場合も、保存済みの下書きと確認状態は受け取れる。Pipelineの実行は既存の利用者操作に従う。

例の時間、手順名、言い回しは試験データに置く。訂正内容、影響箇所、質問の必要性、評価を使う価値はモデルが判断する。

## 2. 現行の接続と追加する契約

現在のレビュー付きbindingは `binding:collaboration.pipeline@3`。保存は `doc.write` / `doc.edit`、評価開始は `collaboration.pipeline.review({ expectedRevision })` を使う。書き込みは版を照合し、既存レビューを無効化する。評価ジョブは実行・結果採用・通知登録の段階で作品や条件を照合する。通知を登録した後は別のDialogueターンで説明を生成するため、ここから会話への保存までを今回の受入に加える。 [Pipeline定義](../../eumenes/api/domains/capabilities/bundles/collaboration.bundle.json#L795) · [作品保存](../../eumenes/api/domains/collaboration/service/work.ts#L158) · [評価ジョブ](../../eumenes/api/domains/collaboration/service/work-reviews.ts#L130) · [通知ターンの確定](../../eumenes/api/domains/dialogue/service/specialist-settle.ts#L173)

| 接点 | 契約と実装先 |
| --- | --- |
| 評価の受付 | `work-reviews.ts` の既存レビュー記録に、受付時の `reviewId`、`workRef`、作品revision、セッションepoch、確定条件と有効な出所のdigestを結び付ける。評価開始時に再照合してから現行文書を取得する。結果側の作品digestもEvaluatorの既存targetから照合する。 |
| ユーザーの訂正 | Dialogueの `stateUpdate` と `supersedes` を使い、状態採用と文書保存の間でも旧評価を現在の参照から外す。作品の保存時は既存のレビュー無効化とQueue取消を使う。条件だけが更新された場合は、旧レビューが表示や再評価受付を妨げないよう、同じ照合を `view` と `start` に適用する。 |
| 支援結果の採用 | 評価完了時の既存の照合を流用する。受付時と同じ対象であること、期限内であること、出所が有効なことを確認する。中断シグナルに従わない遅着結果も拒否する。未完了・失敗・取消の状態は現在の対象に合う場合に限って渡し、確認範囲と未確認事項を区別する。 |
| 通知と最終提示 | 既存の通知イベントを `reviewId` と作品版で識別し、通知推論の入力を作る直前と会話へ書き込むトランザクションの両方で、現行レビューへの一致を確認する。Dialogueは既存のhost参照を利用し、必要なら読み取り専用の照合ポートを狭く追加する。旧版の通知は本文を提示せずに閉じる。同じレビューIDによる二重提示を抑える。 |
| モデルの手順 | Pipeline Skillの評価の節を改訂する。独立照合で重要な条件の見落としを減らせると判断したときに既存ツールを選べるようにする。保存後も評価の判断が必要なら、`doc.edit` の成功返信でターンを閉じず、保存結果を読んで次の行動を選ぶ。評価中、確認できた範囲、修正が必要な指摘、未確認を言い分ける。 |

条件のdigestには評価に渡す確定条件の値と有効な出所を含める。空の状態提案や評価対象と無関係な状態更新だけでは失効させない。状態だけ先に訂正された場合も、現在の条件と旧結果の組を同じ作業として扱わない。通知の組み立て中に新しい前景入力を受け付けた場合は、既存のターン競合制御で表示を保留し、訂正の採用後に再照合する。前景入力の文字列から訂正を判別する処理は設けない。 [状態採用](../../eumenes/api/domains/dialogue/service/specialist-turn.ts#L186) · [状態付き出力の契約](../src/agent/stateful-turn.ts) · [通知受付](../../eumenes/api/domains/dialogue/service/specialist-notices.ts#L77)

通常の版更新は既存のwriterに置き、通知の重複防止と再起動は既存Queueを使う。新規の常駐スケジューラー、作品の保存先、評価の公開ツールは設けない。レビュー記録は既存の `review_json` を使う案とし、受付時のdigestがない旧形式からは最新版確認済みの表示を作らない。履歴上すでに提示した結果は、その時点の版に対する記録として扱う。新しいSkill・package・bindingを登録する場合は空いている版を使い、既存版と並存させる。 [レビュー記録](../../eumenes/api/domains/collaboration/repository/index.ts#L32) · [現行Skill](../../eumenes/api/domains/capabilities/bundles/collaboration.bundle.json#L440)

## 3. 実装順と隔離環境

| 順 | 作業 | 次へ進む条件 |
| --- | --- | --- |
| 1 | Eumenesの確定コミットと必要なPipeline差分を専用worktreeに固定する。Collaboration、Pipeline、Evaluator等の使用版・配布物のSHA-256、lockfile、binding、モデル経路、試験入力を記録する。作業ツリーだけにある差分は対象ファイルを明示し、他作業の未確定差分を持ち込まない。 | 同じマニフェストで起動でき、新規の一時SQLiteから同じbindingを選べる。基準版の既存試験が通る。 |
| 2 | 固定応答と待機用のゲートで、受付後、評価中、通知登録後、通知の会話保存直前に訂正を入れる試験を用意する。既に通る箇所はそのまま回帰試験にする。 | 現行で成立する保護と、新しい照合が必要な区間を区別できる。 |
| 3 | Eumenesの `work-reviews`、Dialogueの通知準備・確定に不足分だけを実装する。既存の状態・権限・Queueの契約を使い、固定試験で段階ごとに検証する。 | 旧版の本文・指摘が採用も提示もされず、同一作品の新しい評価が始められる。 |
| 4 | Pipeline Skillを隔離環境の新しい登録版に接続し、通常会話から編集・評価・提示までを検証する。現行の通常ルートと同じ応答・作品の保存入口を使う。 | 保存された最新版と現在の条件を使ったQuickの結果が、実際の会話記録と作品の表示用データに一度だけ現れる。 |
| 5 | 固定応答の後に、過去と同じLuna 6.0 `low` を使った少数の通し確認を行う。初稿依頼や訂正にツール名を入れず、利用可能ツールだけを提示する。 | 評価を自発選択して始まり、訂正が評価中に入り、最新版の評価が実際に提示された試行を記録する。選択なしと未完了も分母に残す。 |

## 4. 受入試験

固定試験は経過秒数で競合を作らず、Queueの実行開始、評価応答、通知推論、会話保存に合わせたゲートを使う。固定モデルのツール選択は時系列を再現するためのものとし、自発選択の実測は実モデル側で行う。

| 試験 | 成功条件 |
| --- | --- |
| 評価待ち・実行中に条件訂正 | 評価受付時の条件が違えば、未着手の旧ジョブから有効な結果が生じない。実行中は、条件採用後から文書保存までの区間も旧レビューが現在の表示に出ない。遅着させた旧応答は結果採用も通知もされない。 |
| 評価結果の保存・通知登録後に訂正 | 旧通知の推論を始める前、または推論中に訂正を確定させる。どちらも旧版の説明は会話に書き込まれない。前景の訂正が処理され、最新版の評価に進める。 |
| 最新版の保存から提示まで | 訂正後の文書の該当箇所と確定条件が35秒になり、画面確認の条件・出所、未変更の手順ID、元依頼は保持される。Quickの入力版・条件・作品digestが保存済み最新版と一致し、提示した版も同じ。会話の確認通知は一度で、Pipeline実行は開始されない。 |
| 失敗、重複、再起動 | 不完全・期限切れ・取消を適合確認に数えない。Queueの重複受け付けと再起動後も、旧結果の再採用と同じ通知の再送が0件。忘却・世代変更・権限失効の既存試験も維持する。 |
| 評価を選ばない作業 | 転記等の単純な作業を題材に、評価を選ばない固定応答で評価ジョブが0件のまま下書きが確定する。実モデルでも選択の有無を記録し、評価の自動起動は加えない。 |

部分試験は `api/domains/collaboration/test/reviews.test.ts`、本体結合は `api/application/collaboration/collaboration-evaluator.test.ts` を起点とする。Dialogueの状態・通知の回帰も実行する。2026年11月12日の参照作業ツリーでこの4ファイルの既存15テストは通過した。評価と訂正を重ねる試験、および通知保存直前の失効試験はこの計画の追加分。 [既存の実行中失効試験](../../eumenes/api/domains/collaboration/test/reviews.test.ts#L12) · [既存の2版の結合試験](../../eumenes/api/application/collaboration/collaboration-evaluator.test.ts#L37)

実モデルの初回は、訂正が必要な2シナリオと単純編集1シナリオを各2回、計6試行を提案する。各評価の上限は現行どおり120秒。前景は既存bindingの1ターン4回とし、ルーティング・評価・通知も含めた全体上限は暫定で1試行16回、計96回。実行前にマニフェストへ登録し、上限到達は未完了として記録する。訂正シナリオでは、旧評価の実行開始を観測してから訂正を送る。旧評価が選ばれない場合や、訂正との重なりを作れなかった場合は、競合を通過した成功と扱わない。課題ごとに採用版、条件の照合、評価の選択と到達、確認済み範囲、初回応答と提示までの時間、モデル使用量を記録する。

完了条件は、隔離環境で再現できる手順と固定試験が揃い、旧版の採用・提示が全競合試験で0件となること、および最新版を確認して提示する通し経路を保存済みの作品・状態・会話から照合できること。実モデルで自発選択が起きなかった場合は、その結果を明示し、固定試験の接続確認と分けて報告する。
