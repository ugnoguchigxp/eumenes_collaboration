## 1 目的と完了条件

共同作業の条件を失わず更新でき、途中で止まっても安全に再開できる独立coreへ改善する。最初の利用先は既存Eumenesとし、既存のモデル接続、保存writer、queue、権限、描画を再利用する。2026年11月5日のレビューで確認した5件の不具合と、技術品質・利用価値の評価に不足している証拠をすべて対象にする。

先行する目標は、同じ評価基準で技術品質80点以上を実証すること。プロジェクトの可能性も80点以上を目指すが、需要、比較優位、導入負担、継続利用を実測してから判断する。計画の実行や課題数だけで点数を確定しない。

実モデルの検証には、利用者指定のClaude APIとOpenAI APIのLunaを使う。OpenAI側のモデルIDは`gpt-6-luna`とし、Claude側のモデルIDは実行設定で指定して固定する。両providerで条件保持・訂正・終了・復旧を検証し、品質・時間・費用を別々に記録する。

| 完了対象 | 判定条件 |
| --- | --- |
| 既知の不具合 | F01〜F05の受入試験が合格し、元の再現条件で失敗しない。未解決の重大な疑いも残さない |
| 設計 | 意図、終了、工程、ブラウザ要否はLLMが判断する。コードは契約、参照、版、権限、予算を強制する |
| 技術品質 | 全30項目を評価でき、同じlibraryプロファイルで80点以上。未評価項目を除外して達成扱いにしない |
| 利用価値 | 現行方式との比較で、条件保持、介入、完了時間、費用の実測と利用者の受入が揃う |
| 製品採用 | 採用する接続先で移行、取消、再開、忘却、切戻しを確認する。製品採用の承認は別途の実装依頼に従う |
| 記録 | 変更コミット、環境、実配布物、試験、費用、未確認範囲を結び付け、再評価できる |

この計画書の作成は、製品コードの実装、別リポジトリの変更、課金、実外部agentへの送信、公開・デプロイの実行許可を含まない。現在の5件は未修正である。

## 3 既存機構を使う実装方針

実装前に、対象の指示、入力情報、公開操作、hostの実行機構を読み直す。最初に次の修正・再利用を選び、専用機構の追加は右欄の制約を満たす場合に限る。

| 要件 | 修正または再利用するもの | 追加実装を認める範囲と根拠 |
| --- | --- | --- |
| 合成後の状態検査 | collaborationStateSchema、proposeStateUpdate、単一writer | 最終候補の再検査と拒否理由。F01の再現が根拠 |
| 採用と撤回 | Factのstatus・sourceRefs・supersedes、既存の版・出所検査 | 状態遷移の制約のみ。語句から採用の意味を推定しない。F02が根拠 |
| 終了・計画判断 | ModelAdapter、構造化出力、buildCollaborationMessages、s11tnextの固定指示 | 判断結果のschemaと検査。coreにモデルSDKや常駐ループを追加しない |
| 中断後の照合 | hostのqueue・receipt・epoch・外部sessionの正本 | 既存接点で照合できないことを確認した場合だけ、query/reconcileの最小接点を追加。F04が根拠 |
| 入力の資源制限 | 修正済みZod、hostの入力容量・推論予算 | 解析前のサイズ検査と実行制約。F05と測定した資源上限が根拠 |
| 意味品質の評価 | eval/tasks.json、既存のmodel/observation接点、Bunの試験機構 | 現行eval:checkは課題一覧の検査だけなので、記録・実行・比較に必要な最小runnerを追加 |
| 配布と観測 | pack:check、manifest、hostの状態・理由コード・usage記録 | 正本に基づく必要な記録だけ。独立した進捗DB、監視UI、汎用agent基盤を作らない |

発話・題材・サイト名ごとの辞書、正規表現、固定返答による意味判断を増やさない。再現例は回帰課題へ残す。新ライブラリ、独自DSL、汎用plugin機構、別DB、別runtime、全面的な書換えは初期案に含めない。追加が不可欠になった場合は、既存機構の具体的な失敗と代替案、変更範囲を先に記録する。

### W00 基準線と受入契約を固定する

### W01 合成後の状態を検査して原子的に拒否する

- **変更先**: src/agent/state.ts、test/state.test.ts、example/test/state-store.test.ts、状態契約。F01、P0、S。W00に依存。
- **実施**: Mapで組み立てた最終候補を既存のcollaborationStateSchemaで再検査し、成功時だけ返す。上限超過は識別可能な理由で拒否する。hostのtransactionで状態とreceiptを同時に確定する契約を維持する。
- **保存済み異常状態**: 生JSONを保持したまま、既知の件数超過と未知のschemaを区別して診断する。自動削除や過去DBの復元で回復させない。利用者・hostが認めた整理案を新しい操作として適用する復旧手順をW12へ渡す。復旧時にも現在の失効出所を照合する。
- **受入**: 999+1は成功、1000+1は元状態・revision・receiptを変更せず拒否、1000−1+1は成功する。拒否後の正しい更新と忘却が可能。既存入力を変更しない。
- **検証**: 部分のschema境界、結合のSQLite rollback、通しの再開・拒否後再提案。上限を引き上げたり確定条件を切り捨てたりして通さない。

### W02 採用と撤回の状態遷移を強制する

- **変更先**: src/contracts/state.ts、src/agent/state.ts、状態契約、状態試験、evalの却下案課題。F02、P0、M。W00/W01に依存。
- **契約**: proposed/rejected/retractedの代替案は、既存confirmedを失効させない。採用済みの置換だけを撤回処理へ反映する。出所の種類と操作の権限を検査し、利用者の決定をassistantの提案から作らない。何が同じ条件を意味するかはLLMが判断する。
- **実施**: 履歴上のsupersedesと、現在有効な置換の適用を区別する。確定→仮定、却下→再提案、置換鎖、明示的な再採用を契約化する。同じidの更新、removals、既存の置換鎖、host忘却も同じ不変条件に従うか点検する。未確認の経路を既知不具合とは断定しない。
- **受入**: 新しい状態4種×出所種別×既存状態の必要な組合せ、複数の置換、訂正後の却下・再開でも、未採用案が確定条件を撤回しない。採用した訂正、重複id、循環・不存在参照の拒否、忘却は維持する。
- **互換性**: schema/契約版の変更要否をW11で決める。既存レコードの意味を無条件に読み替えない。

### W03 依存を更新し解析前の資源制限を設ける

- **変更先**: package.json、bun.lock、host接続契約、入力境界の検査と試験、依存更新手順。F05、P1、M。W00に依存。
- **実施**: 実装時点で[GHSA-mrhx-c7xc-m3w5](https://github.com/advisories/GHSA-mrhx-c7xc-m3w5)と[修正元](https://github.com/colinhacks/zod/commit/a0ebf970f2d752e5f58527cd2942ff48be4f46bd)を再確認する。修正済み版への最小更新を固定し、Eumenesの共有依存と互換を合わせる。現レビューでの修正版は4.6.6。
- **入力契約**: 文字列/JSONのバイト容量、配列件数、必要なネスト上限、結果容量を、hostの既存上限とW13の測定に基づいて定める。高価な解析前に拒否し、巨大なissue一覧をログへ複製しない。意味や題材の分類はしない。

## 6 意味判断と実行の接続

### W04 終了と計画の判断をLLMへ戻す

- **変更先**: src/agent/session.ts、plan.ts、contracts、index.ts、contexts/collaboration、exampleのmodel接点、対応試験。F03、P1、M。W01/W02とW11の互換方針に依存。
- **実施**: 現在の発話、原文・選択対象、現在版、合意状態、以前の結果、利用可能な操作、残予算を既存メッセージ構築へ渡す。終了・保留・再開、工程・依存・成果、ブラウザ要否と理由を構造化出力として受ける。現行のModelAdapterとschemaによる提案を再利用し、可能な範囲で既存の一回の判断へ含める。追加推論が必要なら理由と費用をW13で測る。
- **撤去対象**: 意味を決めるDONE/THANKS/PREFIX、語句による工程分割・要約・keepOpen、文字列の類似度による判断履歴の選択、無条件の最初のブラウザ使用。参照資料の選択もhostの正本を候補としてLLMへ渡す。新しい単語を足して例だけ通す方式へ置き換えない。
- **残す検査**: 工程数・依存の存在と循環、参照・版、操作の可用性、非負の安全な予算値、残回数、結果容量、採用された構造の整合性。ブラウザ未提供なら実行不可を返す。壊れた判断出力は契約違反として扱い、文字列から意味を補完しない。
- **境界**: completeBriefのように呼出し側が決めたgiven/default/mustAskを整形する処理は維持できる。与えられた値の意味や出所をコードが新たに推定しない。
- **受入**: 疑問、否定、皮肉を含む曖昧さ、言い換え、複数言語、引用、純粋な計算・翻訳、情報取得、複数工程の課題で判断根拠を記録できる。失敗時は指示・情報・道具を修正し、専用分岐を追加しない。コードだけの成功を意味品質の合格にしない。

### W05 外部操作の中断後に正本と照合する

- **変更先**: example/adapters/external.ts、eumenes-terminals.ts、外部接続契約、external試験。F04、P1、M。W00とhostの照合接点の調査に依存。
- **実施**: hostの受付・実行・停止記録、receipt、session世代を照会し、永続化された試行と結び付ける。queuedがhost受付済みか、送信を開始したまま応答不明かを区別する。複数adapterの生成を、プロセス終了と取り違えない。
- **最小追加**: 既存portで状態確認できない場合に限り、対象・request・試行・世代を固定したquery/reconcile接点を追加する。必要な試行識別や有効期限は、既存queueのものを優先する。時刻経過だけで外部操作の完了や未実行を断定しない。
- **復帰規則**: 照合で確定できれば該当状態へ、確定できなければunknownと次に必要な確認を返す。stopping/pendingに永久固定しない。送信・回答の自動再送、許可回答の自動生成をしない。古い試行の応答は新epoch・忘却後の記録を上書きしない。
- **受入**: 送信・回答・停止の前後、受付後で応答前、DB確定前後の実プロセス終了から再開できる。重複副作用なし、他sessionへの入力なし、手入力所有権維持、停止未確認はunknown。外部completedと独立確認済み完了を混同しない。
- **実接続**: 現行terminals bridgeに存在しない質問回答を可用にしない。正式接点と対象が用意された範囲だけ後続で受け入れる。

### W06 意味品質を実行して比較する評価経路を作る

- **変更先**: eval/check.ts、tasks.json、評価runner・結果schema・比較集計、example接点。P1、M。fixture準備はG0から、判断評価はW04後。
- **実施**: 既存32課題の開発/保留分割を維持し、全ターンを実行する。モデル出力、host採用/拒否、原文への出所、現在版、観測の種類、回数・tokens・費用・時間・中断を記録する。expectedはモデルへ渡さない。
- **判定**: 構造検査、意味の一致、実作品の品質を分ける。条件保持、誤った撤回・終了、不必要な確認、捏造、操作権限、保留内容を検査する。自由文の意味判断はLLM/人が担い、決定的なschema・参照・版・禁止副作用の検査をコードが担う。自分の出力を同じ判断だけで合格にしない。
- **公平な比較**: 現行基準と候補を同じ課題、入力、モデル、予算で評価する。開発課題で調整し、保留課題は固定した候補で測定する。必要反復数は事前のばらつき測定と予算から固定し、失敗だけ再実行しない。baselineが同条件で動かないときは比較不能を記録する。
- **受入**: fixtureで欠測・拒否・途中終了・費用不明を正しく残せる。実接続では全群を対象にした記録、人の受入、ばらつきと費用が揃う。保留課題から専用処理を製品コードへ追加しない。

#### Claude APIとOpenAI API Lunaの検証計画

検証用の二つのAPI adapterを、既存の`ModelAdapter.infer`へ接続する。coreへprovider、モデル名、APIキー、HTTP処理を持ち込まない。既存`claude-model.ts`はClaude Agent SDK経由であるため、直接のClaude API試験の成功として数えない。Claude Codeとの外部協働受入も別の試験である。

| 検証先 | APIとモデル | 接続方針 | 合格に必要な確認 |
| --- | --- | --- | --- |
| Claude API | Anthropic Messages API。ClaudeモデルIDはD02で指定 | hostにあるAnthropic接続・usage処理を調べ、移せる最小の変換を検証用adapterへ置く | system/参照/原文の分離、構造化出力、stop reason、usage、取消、拒否と上限終了 |
| OpenAI API Luna | Responses API、`gpt-6-luna` | `openai-api-model.ts`相当の薄い検証用adapterをModelAdapterへ接続 | 入力役割、Structured Outputs、完了/未完了/拒否、usage、取消とrequest ID |

接続先の違いを吸収する範囲は、認証、メッセージ・schemaの表現、応答・usage・エラーの変換に限定する。必要なSDKは既存hostの採用状況と互換性を先に確認し、検証用の開発依存へ固定する。汎用provider frameworkは作らない。APIやモデルの利用権限がない場合は、その系列をblockedとして記録し、別モデルやCLIへ自動で置き換えない。

**接続と契約の受入**

1. 同じ原文、参照、現在版、操作一覧、判断schemaを両adapterへ渡す。providerのメッセージ形式へ変換しても、system・参照・最新の利用者発言の意味と権限を保つ。
2. action、state proposal、W04の判断schemaを両APIへ渡せるか確認する。各APIのJSON Schema対応範囲に必要な表現変換は、既存契約と等価であることを試験する。表現できない制約はhostで必ず検査し、互換性不足を理由に製品契約を弱めない。
3. 正常な構造化出力に加え、拒否、出力上限、未完了、空の結果、不正schema、取消、認証失敗、利用権限なし、429、5xx、切断をfixtureで確認する。実APIでは正常・拒否等の再現可能な範囲を受け入れ、障害を起こすためにproviderへ過負荷をかけない。
4. モデルの返答だけで保存・外部操作を完了させず、同じhost検査とwriterを通す。API検証中は自律的な外部tool実行を与えず、fixtureまたは許可された隔離操作に限定する。
5. 本測定のSDK内部自動retryを明示設定し、隠れた呼出しをusageと予算から漏らさない。受付・費用が不明なtimeoutは成功/失敗を断定せず、新しい課金呼出しへ自動で置換しない。

**比較する単位**

| 段階 | 実施内容 | 完了条件 |
| --- | --- | --- |
| API fixture | 通信をしない応答・usage・schema・異常系の試験 | 二つのadapterが同じModelAdapter契約を満たす |
| 小規模接続 | 両providerでaction/state/判断の代表入力を送る | 指定モデルの利用可否、schema互換、usage・費用推計・取消を確認。費用は総枠に含める |
| 開発課題 | 開発16課題で指示・情報・道具を調整する | 専用語句分岐なしで改善し、反復数・予算・品質閾値を本測定前に固定 |
| 固定候補の比較 | 32課題をClaudeとLunaのそれぞれで、現行baseline/候補・固定反復数Rで実行 | 全ターンの採用/拒否・成果・費用・時間を保存。保留16課題を調整へ流用しない |
| 実host受入 | 両APIで同じ作成・訂正・保留・取消・再開・忘却の主経路を実行 | providerごとの安全不変条件を維持。実作品の受入はW12に従う |

baselineと候補の改善は、まず同じprovider内で比べる。その後、両providerの品質・p50/p95・費用を比較する。成功率をprovider間で平均して一方の失敗を隠さない。R、使用したClaudeモデル、Lunaの有効なreasoning設定、出力上限、service tier、cache条件、並行度、試行順序を記録する。provider間で対応しない設定を無理に同じ値へ揃えず、違いを条件として残す。モデルを変更した結果は別系列にする。

意味の判定には独立した出所照合と人の確認を含める。必要ならClaudeでLuna、LunaでClaudeの出力を評価するが、相互評価だけを正解にしない。判定用モデルは正解を含む別の評価入力を使い、実行役の文脈や権限へ混ぜない。判定の不一致は人が確認し、そのAPI費用も評価費へ含める。

**予算と記録**

検証設定にはprovider、model、APIキーの環境変数名、総費用枠、provider別枠、judge枠、最大呼出し・出力tokens、期限・並行度、retry方針、課題/指示/schema/候補のdigestを持たせる。利用者の共通キーは`.zprofile`の`CLAUDE_API_KEY`と`OPEN_AI_API_KEY`を使い、ログインシェルで`ANTHROPIC_API_KEY`と`OPENAI_API_KEY`へ対応させて起動環境から継承する。プロジェクトごとの`.env`やキー値を持つ設定ファイルは作らない。明示envを指定する隔離試験ではその環境だけを使い、暗黙に親のキーを混ぜない。既存アプリから起動して環境が未反映の場合はログインシェルを経由する。キー値をrepo・課題・結果へ保存しない。Claudeの正確なモデルIDと利用可能な接続、費用枠はD02で確定する。Lunaは公式IDを保持し、利用できない場合も他のモデルに変えない。

基本の評価セル数は`2 provider × 2（baseline/候補）× 32課題 × R`。一つのセルは複数ターンと必要なhost処理を含むため、API呼出し数とは異なる。API費用の見積りは、全ターン・許可された修復・観測・judge・小規模試走・retryを含めて作る。token数はproviderごとに数え、単価・cache・reasoningの課金仕様を混同しない。

レスポンスのrequest ID、実モデル、終了理由、input/output/cache/reasoning等の提供されたusage、処理時間、エラー種別、attempt、課題・候補を記録する。usageと確認日付き単価から算出した費用はestimatedとし、providerが返す確定費用や請求実績と区別する。未提供の項目はnull/unknownとし、0で埋めない。内部推論の本文を取得・保存する前提にはしない。

直接APIでAgent SDKの`maxBudgetUsd`と同じ支出保証が使えると仮定しない。hostの予算台帳、入力見積り・出力上限・実行数・残枠の予約と取消、利用可能なprovider側の支出制約で制御する。費用不明の呼出しは予約枠を解放せず、確認できるまで該当系列を止める。両provider共通の総枠を超える追加試行やjudgeを始めない。

**この検証の受入条件**: ClaudeとLunaの両系列について、fixture→小規模接続→固定課題→実hostの記録が揃い、安全不変条件に違反がなく、D03で固定した品質・時間・費用の条件を満たすこと。一方が未接続・未測定なら、両API対応を合格としない。通常のverify/CIは通信なしを維持し、実API評価は明示したlive入口からだけ実行する。具体的なキー・費用枠は実行前に設定し、今回の計画作成では課金呼出しを行わない。

APIの事実は2026年11月5日に次の公式資料で確認した。LunaのIDとStructured Outputs対応は[OpenAIのLunaモデル資料](https://developers.openai.com/api/docs/models/gpt-6-luna)、出力契約は[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、ClaudeのJSON出力とAPI異常系は[Claude Structured Outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs)と[Claude API errors](https://platform.claude.com/docs/en/api/errors)を参照する。実装時には利用する版と対応範囲を再確認する。

### W07 取消と予算と依存障害を制御する

- **変更先**: example/adapters/claude-model.ts、W06のClaude/OpenAI API adapter、model.ts、external/observation接点、hostの既存取消・usage管理。P1、M。W03/W05/W06に依存。

- **予算契約**: 呼出し前の残枠と実測値を記録する。providerの費用上限が厳密な支出保証かは公式仕様と測定で区別し、保証できない超過リスクを隠さない。期限切れは副作用未実行の証拠にしない。
- **受入**: 遅延、無応答、切断、取消競合、費用欠測、上限直前、並行要求で制御された拒否・停止・unknownになる。再開時に予算を初期化して使い直さない。必要な予算状態はhostの正本へ残す。

### W08 信頼境界と秘密情報を検証する

- **受入**: 複数の実作業・利用者から、再発する課題、現行の手段、所要時間、誤訂正・条件脱落、影響、許容費用を確認する。観測人数・件数・期間と偏りを明記し、少数の便利という感想を広い需要へ一般化しない。

- **受入**: 二つ目の実用途でcoreの再利用と有用性、統合・運用費用を確認でき、資源付きの次段階を判断できる。成果が確認できない間は広い展開を未達のまま残す。

## 9 検証の順序と停止条件

### 部分検証

各作業の対象試験を先に実行する。主な既存入口は`bun test ./test/state.test.ts`、`bun test ./test/session.test.ts ./test/plan.test.ts`、`bun test ./example/test/state-store.test.ts ./example/test/forget.test.ts`、`bun test ./example/test/external.test.ts`、`bun test ./example/test/model.test.ts`。新しい判断契約の移行後は、その契約に沿う対象試験を追加し、旧期待値を変更する場合は仕様上の理由を記録する。

### 結合検証

`bun test ./test ./example/test`でmodel→提案→検査→writer→receipt→再開・忘却を検証する。外部処理は実送信をしないfixture portと検証専用DBで、子プロセス終了・再開まで通す。生成指示を変更した場合は`bun run context:build`で生成し、差分と`context:check`を確認する。

### 通し検証

`bun run verify`、`bun run eval:check`、`bun audit --production --json`を実施する。公開契約・依存・配布物への変更では、固定hostを指定した`PACK_CHECK_REQUIRE_HOST=1 bun run pack:check`を隔離copyで行う。実接続のrunner・性能入口はW06/W13で追加する予定のため、現時点の既存コマンドと混同しない。

旧版との601比較は抽出済みaction/文脈の互換を守る。意図的な新契約は、旧比較を削除せず別の受入を設ける。試験件数は基準値であり、常に同じ件数であることより、重要な期待値を維持したかを判定する。

実モデル・実renderer・実外部agentは、G3後に指定されたテスト設定と予算で実施する。UI変更のない作業へ無関係なブラウザE2Eを増やさない。文書のみの変更ではソース実行試験を省略できるが、リンク・計算・範囲・差分を確認する。

### 停止と再計画

- 同じ目的の「仮説・実施・結果確認」が3ラウンド続いたとき、または新しい根拠のない同一失敗、測定中の編集、計画からの逸脱を認めたときは、次の編集・再実行の前に現状・増えた証拠・残作業を俯瞰し、継続/方針変更/阻害要因を現在の会話へ短く報告する。
- 正常に進んでいる長時間処理は経過時間だけで止めない。再実行する場合は前回から変えた条件を明示する。
- 担当外の失敗、host接点の欠如、費用上限や実対象の未確定は、その影響する工程を止める。独立して完了できる範囲を進め、無関係なrepoやテスト期待値を変更しない。
- 未解決の契約違反、Critical/High、失効情報の復活、無権限副作用がある間は該当機能を採用しない。安全条件・品質閾値を弱めて80点へ合わせない。
