# Eumenes Collaborationの先回り支援計画

2026年11月11日作成 · 2026年11月12日改訂 · 通常返答の開発検証

変更箇所、入出力、比較の判定値、検証手順は [実装計画](proactive-collaboration-implementation-2026-11-11.md) に記載する。

ユーザーが次の作業を逐一指示しなくても、Collaborationが現在の制作から次に必要になりそうな判断を見つけ、材料を揃えておく。ユーザーが判断する前に伝える価値がある場合は、根拠とともに一件提案する。効果は、合意した条件を保ったまま、指示の言い直しや手戻りが減ったかで判断する。

## 今回の判断と作業範囲

- 背景準備で初めて得られた根拠・確認結果は開発用6件中2件だった。本体接続の条件は3件のため、背景準備の接続を見送る。自発提案も保留する。 [背景準備の比較結果](../eval/results/2026-11-12/proactive-ui-a-plus/README.md)
- A+は追加質問が4回から2回になった。差が出た2課題では補足が出ず、会話と作品で得られた判断材料は同等だった。手戻りは両方式とも0件。美術館でA+の1反復が指定の変更を終えられなかったため、A+単独の採用を見送る。 [現行方式AとA+の比較結果](../eval/results/2026-11-12/proactive-ui-a-vs-plus/README.md)
- 現行方式Aの通常返答を見直す。利用者が示した次の判断に必要な材料が足りない場合に、何が未確定かを伝え、確認事項か具体的な選択肢を示す。待機の依頼では待ち、指定の変更で完成とする依頼ではその変更を済ませて終える。開発用6件で先に検証した。 [通常返答の変更・検証](proactive-collaboration-implementation-2026-11-11.md#現行方式aの通常返答)
- 開発用の再試験では、駐車券精算で次の確認案が通常返答に入り、追加質問が全体で4回から3回になった。待機と完成は各2回とも守られた。町内会の窓口が未定の間の案など、追加質問が残った場面は試験記録に残した。 [通常返答の再試験](../eval/results/2026-11-12/proactive-ui-a-reply/README.md)
- 評価用24件を各方式で2反復した。見直し後は最初の返答に代替案と条件が増えた。追加質問は各14回、不要な提案は2件から13件に増えた。完了時の追加案内と応答時間の悪化もあり、見直し後のAの採用を見送る。 [評価用24件の比較](../eval/results/2026-11-12/proactive-ui-a-holdout/README.md)

以下の制作イベント、Agencyとの役割分担、配送規則は、背景準備・自発提案の検討を再開するときに参照する。

初回の対象はUI共同制作の `ui.studio@5` とする。作品の版と出所付きの条件を既存の経路から得られるため、先回りの効果を調べる前に別の制作経路へ条件管理を移植する必要がない。準備は、現在の定義・既存の検査結果・許可された資料を読む範囲で行う。Evaluatorの指摘は将来追加できる観測の一つとし、初回は既存の成果物と条件から判断する。 [UI制作の登録](../../eumenes/api/domains/capabilities/bundles/ui-compositions.bundle.json#L145-L175) · [条件状態の製品接続](../../eumenes/spec/collaboration-state-integration-2026-11-07.md)

## 制作イベントから支援に至る流れ

1. **入力を固定する。** 初回は、UI共同制作の通常返答が確定し、作品または合意済みの条件に実質的な更新があった時点を起点とする。セッションと世代、作品ID・版・digest、条件と出所の版、関連資料を参照する。同じ制作入力への再登録は既存Queueで抑え、計画中の更新は最新入力にまとめる。子作業の結果を単独で起点にするかは拡張時に判断する。
2. **候補を一件選ぶ。** モデルは、次に必要そうな判断とその根拠、準備の内容、先に伝える価値、待てる期限を返す。選択肢は、保留、読み取り準備、根拠付き提案。曖昧な条件でも資料の確認が先にできるなら準備を選び、判断が必要な場合に一問に絞る。入力には採用済み・却下済みの関連候補を含め、意味が同じ提案かの判断はモデルに任せる。コードは参照・形式・版・権限・予算を検査する。
3. **材料を用意する。** 最初は既存定義と既存検査結果を照合する読み取りを一件だけ試す。結果には確認できた事実、仮説、未確認点、資料への参照、依存した条件を残す。結果が古くなったら再利用を止める。準備の実行中も通常の会話を続け、前景処理が始まれば既存の背景推論の制御に従う。 [本体の背景推論](../../eumenes/api/application/agency/llm-port.ts#L91-L131)
4. **次の返答で使うか、提案として届ける。** 次の通常応答に間に合う材料は、その応答で使う。利用者が次に進む前に判断を求める価値がある候補は、入力中・応答中・読み上げ中・休止中を避け、対象が有効な間に一件届ける。提案には、根拠、影響、次に取れる一手を含める。別の通常応答で扱った候補は再送を抑え、明示的な却下と一時保留を区別する。確認が取れない間に候補が失効したら閉じる。

例として、UIの一覧画面がまとまり、次に確認画面を作る見込みがあるとする。Collaborationは、合意済みの「公開は手動」と現在の画面定義を照らし、操作の流れに確認画面を置ける場所を先に調べる。関係箇所が見つかれば、次の返答で候補を示せる。既に確認画面の案があり条件も満たす場合は、同じ提案を繰り返す必要がない。評価課題には、阻害要因を見つける例に加え、まだ頼まれていない次工程の準備が後で役立つ例を含める。

## 本体との接点

- **状態と実行。** Dialogueが条件と出所を所有し、作品の版は制作側から取得する。現行の `collaborationSnapshot` は通常ターンに結び付いた更新処理を含む。背景処理には、必要な作品と条件を一緒に取得できる読み取り接点を追加し、既存の出所検査を共用する。候補と準備結果は条件・承認とは別の派生情報として扱う。キュー、推論、期限、取消、利用量は既存の仕組みに載せる。 [現行の状態取得](../../eumenes/api/domains/dialogue/service/collaboration-state.ts#L26-L99)
- **Agencyとの役割分担。** Collaborationは、担当中の作品と合意条件から、次に取れる制作上の一手と根拠を準備する。Agencyは、会話全体に関わる調査・気づき・自発発話を既存の経路で扱う。CollaborationはAgendaの候補選びを設計の参考にし、候補の生成と状態は自分の制作セッションで管理する。Eumenes本体は、入力・通常応答・読み上げ・休止・出所の有効性を見て、同じ会話に自発提案を出せるかを決める。 [実装計画の役割分担と配送](proactive-collaboration-implementation-2026-11-11.md#agencyとの役割分担と配送)
- **同じ会話で提案が重なったとき。** 利用者の入力と通常応答を優先する。会話が空いていれば、配送の確定処理に先に到達した有効な一件を出す。別の提案元は発話間隔が過ぎるまで出せない。Collaborationとalways-onは有効な候補を保留でき、Fは既存の送信間隔に抵触したときと同じく、その発話を中断する。Collaborationの候補は、次の入力が来た場合や自発提案の期限が切れた場合、有効なら通常返答の補足に回す。候補の生成、会話への保存、利用者の反応を別々に記録する。 [実装計画の配送規則](proactive-collaboration-implementation-2026-11-11.md#同じ会話で提案が重なったとき)
- **操作権限。** 準備は許可された読み取りだけで始める。作品の変更・実行・公開は、対象の版を確認して既存の利用者操作と権限契約に渡す。将来のEvaluatorの指摘やPursuitの結果にも同じ出所と版の検査を適用する。 [ホスト契約](host-contract.md)

## 背景準備・自発提案の実施順と移行条件（保留）

| 段階 | 実施内容 | 次へ進む条件 |
| --- | --- | --- |
| 0. 比較課題の固定 | UI共同制作の基準版と課題を固定し、現行方式を測る。課題には、有用な先読み、次工程を止める問題、待つべき提案、提案不要を含める。判断に必要な根拠と提案の締切を事前に記録する。 | 通常返答と単独で届く提案を同じ方法で観測できる。基準測定、採点基準、反復数、予算、許容遅延が正式比較の登録書に揃っている。 |
| 1. 候補を裏で生成 | 固定入力と実モデルで、候補と保留の判断を記録する。利用者に表示する前に、時期と範囲を人が採点する。 | 独立した複数の課題で、制作上の次の判断を根拠付きで見つけ、保留例と既出の候補を区別できた。 |
| 2. 準備を通常返答で利用 | 対象一種類で、既存の読み取りから準備結果を作り、版を照合して通常返答へ渡す。部分試験、実writer・Queueの結合試験、隔離環境の通し試験の順で確認する。 | 基準より指示の言い直しまたは手戻りが減り、合意条件の充足率を維持した。会話の応答遅延と準備費用は事前の許容範囲内に収まった。 |
| 3. 限定した自発提案 | 次工程の手戻りを避けられる候補を一件、許可された会話で表示する。次の返答だけで使う方式とも比較する。見送り・訂正・停止を通常の会話から受け付ける。 | 段階2より改善する制作課題が複数あり、早すぎる提案や過剰な介入が事前の上限内に収まった。入力中の割り込み、旧版の提示、二重配送は固定試験で0件。 |
| 4. 根拠に応じた拡張 | 待ち時間を活かす再検討、別の制作経路、Pursuitによる長い調査、Evaluatorの指摘の取り込みを個別に試す。 | 各追加が埋める見落としを示し、追加の準備費用と割り込みを含めて単独で効果を確認できた。 |

段階1で候補が弱ければ入力と判断基準を見直す。段階2で準備の再利用だけが効く場合は、その形を先に採用する。段階3の価値が薄い場合は、発話頻度を増やす前に、提示先とタイミングの根拠を見直す。

## 背景準備・自発提案の検証と採否（保留）

同じモデル、初期状態、課題、利用者役、Agencyの設定で、**A 現行方式、A+ 返答への補足、B 背景準備を通常返答に活用、C Bに自発提案を追加**を比べる。開発用6件で候補と採点を調整し、評価用24件は採否の判定に使う。既存のAの48試行は基準の予備記録とし、正式比較では、待機中に届いた提案も含めて各構成を同じ方法で観測する。採点時は構成名を伏せ、利用者役が実際に見た文面と時刻から反応を記録する。固定課題と人の通し試験の両方で採否を判断する。 [基準測定の範囲](../eval/results/2026-11-11/proactive-mode-a/README.md#測定条件) · [比較・観測・採否の手順](proactive-collaboration-implementation-2026-11-11.md#4-比較課題と採否基準)

- **主指標**は、次の作業や既出の条件の言い直し、割り込み等の違反がなく、合意した条件を満たす成果物に到達した試行の割合。課題別に、指示の回数、手戻り、到達できなかった理由を記録する。
- **診断指標**は、次に取れる一手と根拠が揃ったか、判断に間に合ったか、実際に使われたか、余分な提案や作業を増やしたか。保留・見落とし、Agencyとの競合で保留した件数、背景推論の回数と費用、前景応答の待ち時間も記録する。
- **固定試験**では、条件訂正・作品更新・忘却・別の制作への切替、同じイベントの再配送、推論や配送中の再起動、期限切れ、入力中、却下済みの候補、権限不足を確認する。失効した結果の採用、権限外の実行、二重配送は許容しない。障害や未確認を成功に数えない。

再開時は、比較課題と基準を固定し、部分・結合・通しの結果、代表的な成功と失敗、準備と自発提案それぞれの採否を記録する。
