# 品質改善の実装と検証

基準は `b034262`、計画は [品質改善計画](quality-plan-2026-11-07.md)。CIは実施しない。実装開始時点のライブラリの変更は計画3ファイルだけ。Eumenes側には別作業の未commit変更があるため、接続対象と差分を個別に管理する。

## 採用する契約

### 承認の照合

既存の状態schemaと出所検証は維持する。`confirmed` は引用された事実の採用であり、操作権限を表さない。保護操作・重要な決定の利用箇所はホストの既存権限契約が決める。モデルが付ける重要性・承認済みフラグで検査の要否を決めない。

コアに `checkStateApproval` を追加する。ホスト所有の承認台帳に、承認ref、実利用者出所、session・epoch、作品の版、レビューしたfact全体のスナップショット、有効性を保持する。呼出しは保存済み状態・対象fact・承認ref・現在のホスト情報を照合するだけで、承認の発行・意味判断・保存・外部実行は行わない。ホストの正式な承認操作を台帳へ接続する。LLM出力や出所の存在だけから承認行を作らない。

fact・対象版・session・epochが変わった承認、失効した承認や出所、別の決定の承認を拒否する。JSONのobject key順の違いだけでは内容変更とせず、値・型・配列順・出所・置換関係の違いを区別する。無関係の状態更新だけで作品・対象factが変わらない場合は承認を再利用できる。作品の版が変わった場合は対象を再照合する。

専用照合を追加する根拠は、現行の出所検査で観測由来の「公開承認済み」決定が採用される再現である。既存の外部grantと同じ責務分担を、状態内の重要決定にも適用する。発話に応じた分岐は追加しない。

## 実装したもの

- `checkStateApproval` とhost専用の承認記録・保存・失効・忘却。文書内の承認やモデルの自己申告では発行しない。
- 既存行動契約を維持する任意の `createStatefulCollaborationContract`。同じ推論の出力で状態提案と行動を返す。
- 製品の既存writer、推論回数・期限・取消・receipt検査への接続。状態と受付記録を同じtransactionで保存する。
- 実メッセージのIDと内容digestによる出所登録、版の再検査、忘却hook、再起動時の世代更新と保存済み作業の保持。
- 評価の対称反復、各ターンの状態評価、単発率、登録条件・課題hash・実行IDの検査。過去の封印課題・protocol・原ログを可搬なarchiveへ保存。

意味の判断をコードへ移す語句分岐は追加していない。製品の操作権限は既存のimpact・grant・承認経路を使い、`confirmed` を承認へ昇格させない。製品登録は新しいrevisionを追記し、過去の定義・binding・artifact・schemaがすべて残ることを構造比較で確認した。

## 実製品での縦断確認

保存済み設定のCodex接続を使い、`quality-state-20261107` のCLI会話とWebの検証用発言で確認した。Webは会話IDが `main` に固定されているため、検証用と明示した新しい依頼だけを追加した。以前の会話や設定を検証用DBへコピーしていない。

1. 「最初20秒、次30秒、実行せず下書き」の発言から、実モデルが出所付き条件を提案し、製品DBへ保存した。
2. 二つ目だけ45秒へ訂正した。最初20秒と実行しない条件を保持し、画面の手順も20秒・45秒になった。
3. APIとWebを終了して再起動した。同じsession・作品・条件状態が残り、epochが進んだことをAPIで照合し、Webを読み直して表示も確認した。
4. Webで検証用の下書き・条件の忘却を依頼した。通常会話へ戻り、対象sessionのfactsが空になり、作品の表示も終了した。追加の忘却依頼について、記憶担当の `resolve: applied / forgotten`、処理後のエラーなしも確認した。

[訂正結果の画面](../reports/quality-2026-11-07/product-corrected.jpg)、[再起動の照合](../reports/quality-2026-11-07/product-live-main-recovered.json)、[忘却結果](../reports/quality-2026-11-07/product-live-main-forgotten.json)を保管した。製品DBを直接読む代わりに製品APIを使った。タイマーの実行や外部送信はしていない。

副シナリオのCLI会話はモデルの提案で撤回状態になったが、モデルによる下書き消去まで成功したとは扱わない。残った検証用の作業は、その後に既存の認証付きdiscard操作で終了した。主要な受入はWebから作成・訂正した同一作品の経路で判定した。原文出所の失効と遅い提案による復活拒否は、以下の実writer固定試験でも別に確認した。会話履歴全体や別システムの複製の消去は、この受入の保証に含めない。

## 検証結果と範囲

- ライブラリ: `bun run verify`、192件成功、失敗0。型・書式・lint・指示生成・評価課題の構造を含む。
- 承認検査の検出力: epoch、利用者出所、レビュー内容、出所失効の4検査を隔離コピーで個別に無効化すると、すべて試験が失敗した。
- 製品: 内容hashを固定したソースコピーで、対象domainと利用側の1,013件、および画面部品15件が成功。型検査は3,137ファイルで成功。変更対象21ファイルの書式、対象経路のlintも成功。
- 製品の一括verifyは成功扱いにしない。元フォルダでは過去の作業コピーの試験在庫で停止。隔離後は無関係な2ファイルの書式違反で停止したため、既存の違反を緩和せず上記の個別検査で確認した。サイズ制限を超えた今回の関数は責務単位で整理し、対象の制限を満たした。
- 同一機器・同じ入力で基準commitと比較し、通常20件、1,000件、置換の連鎖・密な参照、約2MBの境界を測定した。候補の最大p95は約24msで、既存上限200ms以内。これはコアのローカル測定であり、製品全体の速度向上を示す値ではない。
- 配布物はstrictな固定host試験とresource hash照合を通した。最終の版・archive hashは `dist/*.verification.json` と製品の `vendor/collaboration/provenance.json` に記録する。製品の動作受入後のREADME更新だけを含む再梱包では、実行コードと生成指示の一致を別に確認する。
- 過去の封印評価の主要値27/28/29/29を、保管した課題・protocol・圧縮原ログからオフラインで再現した。過去の測定方法を新しい比較成功と読み替えない。
- production依存のauditで脆弱性報告なし。CIの追加・変更・実行・待機、commit/pushは行っていない。

隔離した製品snapshotの後、別作業でWorldと検証基盤などの8ファイルが変わった。対象外の差分は保持し、今回の製品接続ファイルがsnapshotと一致することを別に照合する。隔離結果をその後の製品全体の検証成功とは呼ばない。

## 費用と未完了の受入

過去の2つの独立台帳を照合すると、実額不明の予約を含む保守計上は14.0745625 USD、総上限15 USDに対する残額は0.9254375 USDだった。以前の7.3088205 USDという説明は片方の台帳だけを示していた。重複call IDはなかった。[照合記録](../reports/quality-2026-11-07/budget-reconciliation.json)を保持し、今回の追加有料API呼出しは0件。製品の実モデル受入は保存済みのCodex接続を使った。

新しい対称の比較は残額で見積りを満たせないため開始していない。台帳を初期化したり、判定条件を減らしたり、少数の受入を大規模比較の代わりにしたりしない。85点超の正式判定には、Cの比較、Dの共通適合試験、Eの製品性能比較の未完了部分を含め、同じ基準での再評価が必要である。長期定着や実利用価値の評価は引き続き別工程とする。
