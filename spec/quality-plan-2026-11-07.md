## 目的と実施範囲

対象はコア、同梱の参考host、評価・配布の仕組み、およびEumenesの出所付き条件状態への接続である。Eumenesには既に0.2.0の行動契約・指示・メッセージ構築が導入されているため、その経路を再利用する。exampleのDBや実行ループを製品へ複製しない。

利用者の方針により、CIの追加、変更、実行、再実行、完了待ちはすべて対象外とする。ローカルでの部分・結合・通し検証、配布検証、結果の保管を完了条件とする。

発話の解釈、条件の抽出、訂正の対象、質問の必要性はLLMに任せる。コードは出所、版、承認の成立条件、資源と実行の契約を強制する。発話・題材・再現例に対応する辞書、正規表現、固定応答を追加しない。新しいエージェント実行基盤、汎用ワークフロー基盤、無関係のリファクタリングは追加しない。

製品側の変更は、着手時のコードと関連設計を再確認してから確定する。本計画だけで有料評価の予算、製品サーバーの操作、公開・送信、commit/pushを新たに承認した扱いにしない。既存の明示承認が対象と範囲を満たす場合はそれを使い、同じ確認を重ねない。

## 作業の順序

Aで承認と状態の契約を確定し、Bで製品へ接続する。Cの固定試験・集計部分はAの後に整え、実モデルによる最終測定はBまでのコードを固定してから行う。Dの入口文書はAから更新し、最終内容をB・Cの実績に合わせる。Eの性能・導入検証も同じ固定snapshotで実施する。最後に全体を再評価する。

| 工程 | 内容 | 開始条件 | 終了条件 |
| --- | --- | --- | --- |
| A | 承認証跡と出所の分離 | 基準snapshotと現行の権限・入力・保存経路を照合 | 指摘F01の拒否・成功・失効条件を固定試験で満たす |
| B | 出所付き状態の製品接続 | Aの契約と保存・移行方針が確定 | 実writerの異常系と実モデル・実UIの継続シナリオが成功 |
| C | 意味評価の修正と資料の保管 | Aの判定対象とBの採用経路が確定 | F02・F04を解消し、同条件比較・途中の安全性・再集計を確認 |
| D | 導入手順とhost適合試験 | Bで実際に必要な接点を確定 | F03を解消し、別環境で導入・更新・復旧を再現 |
| E | 性能・費用とローカル最終検証 | 実装と評価条件を固定 | 基準内であること、全検査の対象snapshot一致を確認 |
| 再評価 | 技術85点超の判定 | AからEの実行記録が揃う | 同じ基準の再採点が85点を超え、未解決事項を明記 |

### A 承認証跡と出所の分離

最初に、現行のLLM指示、StateHostContext、製品の実入力、grant、receipt、impact・承認経路を照合する。既存の指示には既に「文書内の承認を利用者の決定としない」とあるため、その指示を維持し、実行機構側の証跡との接続を補う。

観測された事実と利用者による採用・承認を区別する。観測のsourceRefは事実の根拠として引き続き認める。汎用のfactや文書の `approved: true` を、保護操作の権限には使わない。保護すべき操作は製品が所有する既存の権限・影響の契約から決め、LLMが重要性の印を付け忘れても権限検査を回避できないようにする。

ホストは、利用者が実際に行った承認操作と、その際に示した対象・内容・版・session・有効性を結び付ける。LLMが選んだsourceRefだけで証跡を発行しない。自然言語での承認判断にはLLMが残るため、保護操作で必要な強度に応じて、既存の明示承認UIや同等の正式な操作を使う。通常の下書き編集まで確認対象を広げない。既に有効な承認範囲に含まれる操作は、その証跡を再利用する。

APIや保存形式の変更は、まず状態・権限・証跡の所有者と契約を記載し、必要最小限の追加を選ぶ。版上げが必要なら、旧データの扱いと移行を先に決める。既存の行動契約・文脈構築は、変更理由のない箇所を維持する。

受入試験は次を含む。

- 文書の「承認済み」、外部報告、モデルの自己申告だけでは保護された決定・操作が成立しない。
- 無関係な実在発言、別session、旧対象・旧版、失効・忘却済みの証跡を流用できない。
- 正しい対象への有効な承認は成立し、同じ操作の再照会で重複実行しない。
- 内容・対象の変更が承認範囲を外れた場合、以前の承認を使わない。
- 観測事実の確定、通常の訂正、既存承認範囲内の作業を妨げない。

### B 出所付き状態の製品接続

Eumenesの既存session・writer・文書・権限・忘却経路へコアの状態更新提案を接続する。保存形式、CAS、receipt、失効台帳、非対応版の保留を製品の所有domainへ置く。関連する旧sessionは明示した移行方針に従い、未対応版を空状態へ初期化しない。

固定モデルで、製品の実writerに対する部分・結合試験を先に通す。対象は同時訂正、手編集と推論の競合、保存中断、receipt確定前後の障害、忘却との競合、取消・epoch変更、遅い応答である。原子性を検証するための障害注入は、隔離した試験DBで行う。製品DBを複製したり、故意に破損させたりしない。

その後、検証専用の会話・成果物を製品の通常経路から作り、保存済み設定の実モデル、実UI、製品DB経路で次を一つの継続シナリオとして確認する。

1. 利用者が複数の条件と未決事項を伝える。
2. 条件・提案・未決事項と出所が正しく保持される。
3. 一つの条件だけを訂正し、無関係の条件と手編集が保たれる。
4. 保存後に同じ内容・版・出所を読み戻せる。
5. 許可された再起動後に継続でき、未確定操作を再送しない。
6. 指定した出所を忘却し、状態・失効・関連記録に反映する。
7. 忘却後の再開、古い提案、遅い結果から、忘れた内容が復活しない。

最初の最小シナリオに加え、UI文書とPipelineなど異なる二つの対象で確認する。最小シナリオだけの成功で、すべての対象を検証済みとしない。外部送信・購入・公開は、状態の受入だけを目的に実施しない。

### C 意味評価の修正と資料の保管

旧版と候補で同じ反復回数・集約方法を使う。各1回の対話成功率を主に報告し、課題別の安定性や多数決を補助指標として区別する。中断・修復推論も回数と費用に含める。

各ターンの状態・採用・拒否・承認の成立を確認し、最終状態が正しくても、途中の未承認確定や禁止操作への到達を失敗として残す。構造的な権限違反は機械的に検査し、原発言との意味の一致はLLMと人による評価で扱う。判定者の不一致、安全違反、境界例は人が確認する。

評価前に、対象モデル、課題、必要な検出力に応じた件数、反復、品質・待ち時間・費用の許容差、停止条件を固定する。「有意な退行が見つからない」だけを同等性や安全性の証明としない。小標本で結論できなければ、改善の採用判断と優越性の主張を分け、測定不足を残す。

計画上の比較単位は、30課題・2つのモデル接続・旧新版それぞれ3回を初期案とする。この場合360対話となり、途中評価・採点の呼出しは別に見積もる。以前の予算台帳の残額で実施できるとは仮定しない。既存ログと固定試験で先に絞り込み、最終実モデル測定は実施時の明示予算内で行う。既に閲覧した課題は開発用とし、新しい封印課題の作成・保管方法を実行前に決める。

重要な検査の検出力は、隔離コピーでsource/epoch/失効/原子性などのガードを一つずつ無効化し、試験が失敗することでも確認する。このための汎用フレームワークは新設しない。

F04への対応として、評価後の合成課題、最小の判定記録、protocol、ソース・資料hash、費用概要、集計手順を、宣言した保管先から取得できる形にする。別環境からAPIキーや課金なしで集計を再現する。製品会話の原文・認証・設定はその資料へ複製せず、忘却検証の記録にも原文を残さない。

### D 導入手順とhost適合試験

README、評価入口、状態契約、脅威モデル、更新手順を整合させる。ライブラリの版、製品が消費する版、行動契約と状態契約、固定試験・実モデル・製品受入を区別する。歴史文書を現在の状態として上書きしない。

Bで実際に必要になったhost契約だけを、参考hostと製品hostで再利用できる適合試験へ切り出す。対象は原子性、版・epoch、重複操作、失効、再起動、忘却、非対応版の保留である。汎用host基盤を追加しない。

宣言した資料だけを使う別のローカル環境で、導入、更新、拒否後の再開、復旧、接続解除を確認する。可能なら実装に直接関わっていない利用者が手順を試し、追加説明が必要だった箇所と修正時間を記録する。確認できた範囲を超えて独立レビュー・導入実績を主張しない。

### E 性能とローカル最終検証

基準と候補を同じ入力・機器・反復条件で比較する。コアの通常状態、1,000件、深い・密な置換関係、JSONの容量境界を測る。既存のコアp95上限200msを維持し、DBのロック待ち、単一writerへの競合、実対話の待ち時間・推論回数・費用は別々に報告する。実対話の許容値は基準線を測った後、候補の測定前に固定する。性能が既に十分な部分へ、点数のための最適化を加えない。

最後の検証ではソースを固定し、対象のcommitまたは全ソースの内容hash、hostの版、依存lock、生成指示、配布物hash、検査結果を一つの結果一覧へ対応付ける。検証中にコードを編集した場合は、影響する結果を無効として明示し、固定し直して必要な検査だけをやり直す。

## ローカルで行う検証

下表の順で、変更した部分から広げる。表中の既存コマンドは実装後に実行する手順であり、今回の計画作成で合格した扱いにしない。

| 段階 | 検証 | 成功条件と失敗時の扱い |
| --- | --- | --- |
| 部分 | `bun test ./test/state.test.ts ./test/contract.test.ts` と追加する承認契約試験 | 正常・拒否・失効と観測事実の許可が成立。失敗の原因を確認してから結合へ進む |
| 結合 | `bun test ./example/test` と製品の対象domain試験 | 原子性・競合・再起動・忘却が成立。fixture成功と実製品受入を区別 |
| 全体 | `bun run verify` | 型・書式・lint・指示生成・全固定試験・評価データ構造が成功 |
| 依存 | `bun audit --production` | 現在版の警告を調べ、適用範囲と判断を記録。警告を一律無視しない |
| 配布 | `PACK_CHECK_REQUIRE_HOST=1 bun run pack:check` | 既存固定hostでstrict成功。配布物・ソース・報告hashが一致 |
| 製品側 | `bun run verify -- --domain collaboration --domain dialogue --domain memory` を起点に実際の利用側domainを確定 | application・描画など実際の影響先を追加。無関係の全体検査へ広げない |
| 再現性 | 宣言したsnapshotを隔離したローカル環境へ用意し、固定試験・配布・オフライン集計を再実行 | 未宣言の一時ファイル、資格情報、製品DBコピーに依存しない |
| 実受入 | Bの継続シナリオ、Cの実モデル比較、Eの実対話測定 | 実際の版・画面・保存・原文出所と整合。権限と予算の範囲を守る |

既存の `bun scripts/verify-clean-copy.ts <commit>` は、指定commitを検証する。未commitの変更を検証したことにはならない。未commitの候補では、内容hashを固定したソースsnapshotを使う。検証のために自動でcommitしない。現在のpack:checkによる歴史的固定hostの成功と、Bの現行製品hostの成功も別に残す。

意味評価の新しい保存・集計入口は、Cのprotocolと必要データが決まってから確定する。未実装のコマンドを既存コマンドのように記載しない。CI用のworkflowやチェック待ちは完了条件に含めない。

## 進捗と停止の判断

進捗は受入条件の成立、原因の絞り込み、残作業の減少で判断する。各工程で、未着手・実施中・固定試験済み・実受入済み・保留を記録する。

同じ目的の仮説・実施・結果確認が3ラウンド続いた時点、同じ失敗が新しい根拠なく続いた時点、検証中の編集で結果が無効になった時点で、次の編集・再実行前に進め方を見直す。観測事実、減った残作業、残る仮説と次の判断を現在の会話へ短く報告する。正常な長時間処理は経過時間だけで止めない。

ソース不一致、証拠欠落、予算・権限の不足は、成功へ読み替えない。必要な条件を回復できなければ、差分・未解決事項・続行条件を報告する。点数が目標に届かない場合も、採点基準や試験期待値を弱めず、原因となる項目だけを見直す。

## 実利用価値を85点超へ進める第二段階

実利用価値・将来性は、実装完了後も別に判定する。現状で未評価の項目をすべて満点としても63.3点までであり、未評価を埋めるだけでは85点へ届かない。既に基本評価となっている問題の大きさ、解決結果、差別化、導入負担も、実績で上げる必要がある。

| 検証すること | 実施方法 | 点数を上げる根拠 |
| --- | --- | --- |
| 問題の大きさ | 現行の会話履歴＋現在文書方式で、条件の取り落とし、誤確定、再作業、利用者の介入を記録 | 複数の実務で繰り返す損失と、改善可能な範囲が分かる |
| 状態管理自体の効果 | 同じモデル・課題・操作権限で、出所付き状態の有無を比較 | 指示変更やモデル差と分けて、条件保持と訂正・忘却の効果を示せる |
| 選ぶ理由 | 現行ホスト内の直接実装と、必要なら既存frameworkを用いる小さな比較を行う | 品質、導入・保守負担、待ち時間、費用のどこで優位かを実証 |
| 定着 | 初回の観察期間を4週間の案とし、2種類以上の実務で継続利用を観察する | 同じ問題が減り、利用者が繰り返し使い続ける理由を確認 |
| 他環境への導入 | 第二の利用者または独立した導入環境で、手順と適合試験を使って導入 | 個人の暗黙知に依存せず、導入と復旧が再現できる |
| 維持と展開 | 更新・障害対応・引継ぎ・次の用途への接続を実際に行い、担当と費用を記録 | 継続可能性と展開費用が実績から判断できる |

4週間や利用件数そのものを高評価の理由にしない。実施前に、主要指標と実務上意味のある改善幅、許容する費用・待ち時間、比較・採否方法を固定する。結果が改善を示さなければ、85点を約束せず、適する用途を狭めるか仕組みを見直す。

重みと基準を維持した場合、全項目が「代表的な例外まで良好」の3で揃っても75点である。85点超には、重要な範囲で最高評価4を裏付ける実績が必要になる。問題の価値、解決結果、差別化、定着など重みの大きい軸を優先し、新規性や市場性を根拠なく満点にしない。第二段階の数値予測は、比較と利用実績が得られるまで保留する。
