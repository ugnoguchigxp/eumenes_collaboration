# Eumenes Collaborationの先回り支援 実装計画

[先回り支援の方針](proactive-collaboration-plan-2026-11-11.md) に基づき、`ui.compose` の `ui.studio@5` で、次の制作判断に必要な材料を現行方式Aの通常返答で示せるかを確かめる。Collaborationリポジトリで共通指示、開発用課題、採点方法、比較結果を管理する。 [対象binding](../../eumenes/api/domains/capabilities/bundles/ui-compositions.bundle.json#L145-L175)

初回の現行方式の測定はEumenes `4ed26d7f` を使用した。開発用の再測定にも同じホストを使う。 [現行方式の登録](../eval/results/2026-11-11/proactive-mode-a/registration.json)

## 現行方式Aの通常返答

背景準備の本体接続とA+単独の採用は、開発用の比較結果を受けて見送った。現行の通常ターンで、作品と会話から判断できる場合は今の依頼を済ませ、結果を短く伝える。次の判断材料が足りない場合は、未確定事項とその影響、確認事項か実行可能な選択肢を既存の `text` に収める。確認中の待機を求められた場合は、待機だけを返す。指定した変更で完成とする場合は、対象を作品と会話から特定して変更し、結果を伝えて終える。 [背景準備の比較](../eval/results/2026-11-12/proactive-ui-a-plus/README.md) · [AとA+の比較](../eval/results/2026-11-12/proactive-ui-a-vs-plus/README.md)

返答の判断は、通常ターンで既に使う共通指示に記述する。会話、作品、条件の既存入力と、現行の操作・返答契約を使う。未定・未提示の情報が必要なときは、確認が済むまでに取れる案と、誰に何を確かめるかを示す。変更に関わる未確認の手順は、作品と返答で確認中または条件付きの案として扱う。提案した案を実行するには、通常の依頼・権限の条件に従う。 [共同制作の共通指示](../contexts/collaboration/rules.context.toml)

1. `bun run context:lint` と `bun run context:check` で、指示の形式と生成物の一致を確認する。
2. 先行試験と同じ隔離ホストのCollaborationカタログに変更を反映する。開発用6件の固定応答で、変更した指示が通常ターンに届き、初稿・条件が同じ状態で再開することを確かめる。
3. 同じ開発用6件を各2反復し、前回のAの記録と比較する。同じモデル、初稿、観測時間、利用者役を使う。追加質問が減った場合は、返答と作品を直接照合し、次の判断材料が実際に増えたかを確認する。待機と完成は全反復で、返答と作品の変更の両方を検査する。評価用24件は共通指示を固定した後に実行する。 [比較手順](../eval/proactive/README.md)

再試験では追加質問が4回から3回になった。駐車券精算では通常返答に確認案が入り、追加質問が1回減った。授業アンケートの待機と美術館の完成指示は各2/2で満たした。町内会では公開窓口が未定の間の案、工作教室では主催者に尋ねる項目の具体化が残った。手戻りは変更前後とも0件だった。 [開発用6件の記録](../eval/results/2026-11-12/proactive-ui-a-reply/README.md)

未確認の手順と確認待ちの扱いを見直した試験では、町内会の両反復で未確認の取り次ぎを確定扱いせず、工作教室の両反復で主催者と確認内容を示した。追加質問は3回から2回となり、待機と完了は各2/2だった。町内会の代替の受付方法は、両反復とも追加質問後の提示だった。 [未確認の手順と確認待ちの試験](../eval/results/2026-11-12/proactive-ui-a-confirm/README.md)

当初の手段が使えない場合の別の方法と、その方法自体の実施条件を、作品を更新した直後の通常返答に含めるよう見直した。残した指示では、町内会の1/2反復で最初の返答に代替手段と条件があり、全体の追加質問は2回から1回になった。待機と完了は各2/2。町内会の反復間の差と、社食で出た不要な提案1件を試験記録に残した。 [代替手段の試験](../eval/results/2026-11-12/proactive-ui-a-alternative/README.md)

続く試験では、前の手段が使えるようになるための確認と、その手段を使わずに目的を進めるための実施条件を共通指示で区別した。判断材料を既存の方法で利用できる場合は、参照先を伝えて終える。残した指示では、町内会の両反復で代替案と実施条件が最初の返答に揃い、社食の不要な提案は0件だった。追加質問は全体で0回、待機と完了は各2/2。 [判断材料と代替手段の試験](../eval/results/2026-11-12/proactive-ui-a-decision/README.md)

固定した共通指示で評価用24件を各方式2反復した。阻害要因の通常返答で代替案または暫定対応と実施条件が揃ったのは0/12から11/12。追加質問は各14回、不要な提案は2件から13件だった。準備・阻害要因で改善2課題、悪化4課題。完了時の不要な追加確認と応答時間の基準超過もあり、採用を見送る。 [評価用24件の比較](../eval/results/2026-11-12/proactive-ui-a-holdout/README.md)

代替案を示す範囲を、今頼まれた結果に必要な手段が使えず、今回の作業が止まる場合に絞った。未使用の12課題で、阻害要因の6試行すべてに代替案と実施前の確認事項があった。待機・完了は各6/6。不要な提案は両版とも0件で、減少は確認できなかった。鍵の受け渡しの1反復で予約確認の方法が足りず、追加質問が発生した。 [範囲を絞った比較](../eval/results/2026-11-13/proactive-ui-a-narrow/README.md)

## 1. 最初の対象と実行モード

以下の第1〜6節は、背景準備・補足欄・自発提案を再検討するときのための設計記録。現在の着手範囲は上記の通常返答に限る。Agencyの接続先はEumenes `b59dda83` 時点の構成と現行コードを参照している。

最初の起点は、成功したUI共同制作の通常ターンの終了時とする。対象は `reply` で確定したターンに限り、ホスト観測のターンと、担当を離れる `return`・`discard` は起点にしない。作品の定義または確定条件に実質的な更新があり、作品が存在する場合に計画を一度起動する。たとえば一覧画面を整えたところで、合意済みの「公開前に確認する」という条件から、次に必要になりそうな確認画面の選択肢を、既存の画面定義と検査結果に沿って整理する。

準備の対象は、通常ターンが同じ入力と推論回数では行えない確認から選ぶ。通常ターンと同じ材料を読み直すだけの準備は、背景処理を作る理由にならない。第一候補は、確定済みの条件を一件ずつ定義の全文と照合する確認とする。通常ターンには大きな定義が概要として渡される場合があり、返答も二文・300字に収める必要がある。どの確認を採るかは工程1の採点で決める。背景処理は読み取りだけで完結し、作品を占有しない。計画中も通常ターンと画面からの編集を受け付け、版の照合で古い結果を失効させる。UIからの手編集やUndoは初回から失効判定に使い、単独で計画を起動する範囲は後続の比較で判断する。 [通常ターンへの文書の渡し方](../../eumenes/api/domains/dialogue/service/specialist-memory.ts#L145-L157)

隔離した試験ホストで以下を切り替える。既定はA。モードはセッションの開始時に決めてセッションと各記録に残し、途中では切り替えない。候補だけを採点する段階では、試験用の記録に限定する。モデルと接続先は既存設定から取得し、比較中は同じ経路を固定する。

| モード | 挙動 |
| --- | --- |
| A 現行 | 現在の共同制作をそのまま実行する。出力契約と推論入力は現行と一致させる。 |
| A+ 補足欄のみ | 背景処理を使わない対照。通常のモデルが同じ呼出しの中で、次に必要な判断を補足欄に書く。表示と文字数の上限はBと同じにする。 |
| B 準備 | 背景で用意した有効な準備結果を、次の通常の返答で補足として使う。 |
| C 準備と自発提案 | Bに加え、次の返答まで待つと判断が間に合わない候補を、空いた時点で一件だけテキスト表示する。 |

A+を置くのは、BがAに勝った理由を見分けるためである。Bは、返答の枠の外に補足を出せることと、推論を一回多く使えることの両方でAより有利になる。A+で前者を揃え、背景での準備と検査に固有の効果だけをBとの差として測る。

## 2. 実装箇所と順序

本体への配線は、候補の質と補足欄の効果を確かめた後に行う。各工程は、次へ進む条件を満たした場合だけ次に進む。

| 工程 | 変更する箇所 | 実装と引き渡し条件 |
| --- | --- | --- |
| 0. 比較基準の固定 | Collaborationの `eval/` と隔離試験ホスト | 現行方式の試験経路を起点に、ターン外で会話に追加された提案まで観測できる収集方法を用意する。§4の登録を確定し、正式比較のAを同じ収集方法で採取する。工程1で使う開発用課題の定義・条件・出所は評価用の記録と分けて保存する。 [先回り支援の課題と集計](../eval/proactive/README.md) · [現行方式の実行コード](../eval/results/2026-11-11/proactive-mode-a/live-runner.ts.txt) |
| 1. 候補の質をオフラインで確認 | Collaborationの `eval/` | 開発用6件の固定入力から、評価ハーネス上で実モデルに候補・保留を生成させる。人が構成を伏せて、根拠の正しさ、時期、範囲、通常ターンの入力だけでは得られない確認を採点する。準備の対象を複数試し、採る確認を一つに決める。進む条件は§4の「候補を接続する」。満たさなければ開発用課題で入力と判断基準を見直す。 |
| 2. 補足欄と対照A+ | Collaborationの出力契約、Dialogueの出力確定 | 返答の本文とは別に表示する補足欄を、状態更新つき契約と同じopt-inの契約として追加し、Eumenesの同梱パッケージを更新する。開発用課題で工程1の候補とA+を比較し、候補にしかない根拠や確認結果を記録する。A+の振る舞いを固定してから、正式比較でAと比べる。 [現行の出力契約](../src/agent/action.ts#L26-L44) · [opt-inの契約](../src/agent/stateful-turn.ts#L7-L40) · [回答の保存](../../eumenes/api/domains/dialogue/service/specialist-settle.ts#L189-L201) |
| 3. 固定入力と候補の生成 | EumenesのDialogue、UI制作adapter、Inference | Dialogueに、既存の出所検査を共用する読み取り操作を置く。UIの文書読出しと定義検査を再利用する。通常ターンを確定する `settleSpecialistTurn` の中で、実質変更があれば最新の入力を同じwriterでQueueへ登録する。登録できない場合（容量超過など）は起動を見送り、通常ターンの確定は巻き戻さない。既存の背景推論（`captureBackgroundControlInTransaction`）で構造化された候補を生成する。経路は `route: "conversation"` を明示する。省略するとローカル限定の経路になり、通常ターンと条件が揃わない。締切と出力量は構造化出力の既存上限（300秒、2400トークン）の範囲で決める。試験用の記録で、工程1と同等の候補が本体の経路でも得られることを確かめる。 [ターンの確定](../../eumenes/api/domains/dialogue/service/specialist-settle.ts#L132-L201) · [UIの定義読出しと検査](../../eumenes/api/application/media/ui-compositions-adapter.ts#L311-L346) · [背景推論](../../eumenes/api/domains/inference/service/background-control.ts#L72-L145) |
| 4. 準備結果を通常返答へ | Collaborationの出力契約、Dialogueの通常ターンと出力確定 | 固定した資料の確認結果を候補として保持する。試験用の出力契約に候補IDの選択欄を追加し、関連性の判断は通常のLLM呼出しで行う。選ばれた補足を、出力確定時に有効な場合だけ工程2の補足欄に表示する。通常ターンの推論回数を維持し、BをAとA+の両方と比較する。 [推論入力](../../eumenes/api/domains/dialogue/service/specialist-turn.ts#L433-L476) |
| 5. 自発提案の配送 | Dialogueの会話配送と本体のAgency接続 | Bの採用後、§3の役割分担と配送規則を既存の会話保存経路に接続する。会話が空いている間に、先に知らせる価値がある候補を一件だけテキスト表示する。Agencyの両モードとの競合を§5の固定試験で確認し、§4の観測方法でBとCを比較する。 |

方針文書の段階との対応は、工程0が段階0、工程1と3が段階1、工程2と4が段階2、工程5が段階3である。

工程3の背景用読出しでは、既存の `collaborationSnapshot` のうち検証だけを共用する。この関数は通常ターンの `runId` を使って出所を登録し、失効も保存するため、背景処理の入口としてそのまま呼び出すと状態の書込みを伴う。読み取りで無効な出所が見つかった場合は、保存せずに、その出所に依存する条件を除いた状態を入力にする。編集済み・忘却済みの原文は背景推論へ渡さず、失効の保存は次の通常ターンに任せる。文書本文は現行の正規化済み定義を使い、必要なら現行validatorを読み取りで実行する。作品の画面表示や動作については、実際に確認した材料がある範囲を記録する。 [現行の条件取得と登録](../../eumenes/api/domains/dialogue/service/collaboration-state.ts#L26-L160) · [正規化されたUI文書](../../eumenes/api/domains/ui-compositions/service/work.ts#L114-L125)

## 3. 入出力と採用条件

| データ | 最小の項目と扱い |
| --- | --- |
| 固定入力 | `sessionId`、`epoch`、binding版、作品ID・版・digest、条件・出所の版、提示資料のID・位置、直近の制作目的と確定済みの条件、関連する過去候補。入力の範囲と実際に提示した出所をホストが記録する。 |
| 候補 | ホスト発行ID、保留・準備・提案の選択、次に必要な判断、根拠の参照、観測と仮説、推奨する次の一手、早めに伝える理由、未確認点。LLMが根拠の意味と関連性を判断する。ホストはID、参照位置、サイズ、利用可能な操作を検査し、自発提案の締切を記録する。 |
| 実行と結果 | 入力識別子、実行世代、モード、Queueジョブと推論の受付・結果、候補または終了理由、期限。結果は `保留`、`有効`、`失効`、`中断`、`失敗` を区別する。準備済みと配送済みは別に記録する。 |
| 提示と反応 | 候補ID、配送先会話、応答のメッセージID、提示経路、利用者の見送り・却下・訂正・停止。モデルが反応の意味と候補の対応を読み、ホストが実在する利用者発言・対象候補・会話を照合する。 |

新しく設ける保存先のテーブルと欄、出力契約の欄名は、工程2・3の着手前にこの文書へ書き足す。名前を決めずに着手しない。

- **起動と競合。** Queueにセッション単位の同時実行キーを付け、同じ入力は一度だけ受け付ける。重複防止のキーは入力識別子から作る。同じキーで内容の違う登録は既存Queueが拒否するため、payloadは入力識別子に限る。ジョブは背景レーンに置く。計画中に入力が変わったら、旧結果を失効させ、実行が落ち着いた時点で最新の入力だけを計画する。ジョブは開始時に自分の入力がセッションの最新かを照合し、古ければ推論せずに失効で閉じる。起点は作品と条件の実質変更。状態版は追跡用に残し、空更新や新しい出所の登録だけで不要な計画を起こさない。初期値は、一入力につき背景推論一回、保持する候補一件。締切・入出力上限・費用は工程0で固定する。 [既存Queueへの登録](../../eumenes/api/domains/queue/service/index.ts#L65-L105) · [状態版の更新](../src/agent/state.ts#L149-L155)
- **保存の所有者。** Dialogueがセッション単位の最新入力と有効候補を所有する。製品接続で永続化する際はDialogueの既存migration経路を使う。Queueには識別子だけを渡し、候補本文や出所の原文を複製しない。却下・配送の記録には照合に必要な範囲を残し、期限切れや忘却を既存のライフサイクルに接続する。明示的な停止は対象会話・セッションに保存し、再開まで自発配送を抑える。
- **保存と再確認。** 結果採用時と表示直前に、セッションが有効であること、セッション世代・binding・作品版を再検査し、実際に提示した条件の値・状態・出所の有効性を照合する。出所台帳の版が変わった場合は、提示した参照の中身を再照合する。実質変更を見分ける比較は正規化した構造に対して行う。意図や提案の意味は文字列の重なりで判定せず、モデルに既出候補と根拠を渡す。忘却時は依存候補の本文と参照を既存の忘却トランザクションで削除する。発行済みの推論結果が再起動後に不明なら中断として閉じる。 [条件の忘却処理](../../eumenes/api/domains/dialogue/service/collaboration-state.ts#L255-L293)
- **補足欄。** 返答の `text` は読み上げを前提に二文・300字までに制限されている。補足はこの枠に含めず、文字数の上限を別に定めたテキスト表示とし、読み上げの対象にするかは工程2の着手前に決める。A+とBで表示と上限を同じにする。返答が外部出力へ引き渡され、会話にメッセージが残らない場合は補足を添えない。Bではその候補を未消費のまま残す。 [返答の制限](../../eumenes/api/domains/delivery/service/speech-reply.ts#L3-L4) · [回答の保存経路](../../eumenes/api/domains/dialogue/service/specialist-settle.ts#L44-L60)
- **通常返答の保護。** モードBでは、通常のモデルに候補IDと対象・用途の短い見出しを渡す。結論や提案文は、出力確定時にホストが補足欄に表示する。通常本文や操作に未検証の準備内容が混ざると、作品を編集したあとに古くなった情報だけを取り除けないためである。補足を選んでも、同じターンで作品や関連条件が変われば、本文を保存し補足を落とす。候補IDで付与するのは表示の選択だけで、操作の権限には使わない。

### Agencyとの役割分担と配送

| 担当 | 判断と責務 |
| --- | --- |
| Collaboration | UI共同制作の最新の作品・合意条件・有効な出所から、次に必要な制作上の判断と根拠を準備する。モデルが一手を示すか、材料だけ残すか、待つかを判断する。候補は制作セッションに結び付ける。 |
| Agency | 会話全体を対象に、既存のFまたはalways-onで調査・気づき・自発発話を判断する。Agendaの候補生成や既存資料の確認をCollaborationの設計の参考にする。候補と調査状態は各機能が所有する。 [Agendaの計画](../../eumenes_agency/src/agenda/plan.ts#L48-L114) · [Agendaの既存資料確認](../../eumenes_agency/src/agenda/check.ts#L23-L85) |
| Eumenes本体 | Dialogueの会話保存に接続し、会話単位で自発提案の配送を調停する。入力・前景処理・読み上げ・休止、発話間隔、候補の期限と出所、各機能の設定を照合する。意味の近さや提案内容の優劣の判断はモデルが担い、本体は既出の文面を必要な範囲で参照として渡す。 |

AgencyのFとalways-onの既存の発話保存・Live音声への引き渡しと、Collaborationのテキスト追記を同じ会話の調停に通す。現行の `claimAgencyDispatch` はAgencyの世代と保存状態を照合するため、各モードの既存検査として使う。共通の照合には会話ID、提案元、候補またはチケットのID、配送の確定時刻を使う。既存の会話・配送記録を利用し、Liveへの引き渡しも会話単位で追えるようにする。 [Fの発話保存](../../eumenes/api/application/agency/delivery.ts#L112-L142) · [always-onの発話保存](../../eumenes/api/application/agency/always-on-flow.ts#L183-L225) · [Agencyの配送間隔](../../eumenes/api/domains/dialogue/repository/agency.ts#L31-L46)

### 同じ会話で提案が重なったとき

1. **通常の会話を優先する。** 入力中・前景処理中・読み上げ中・休止中は自発配送を保留する。サーバーが新しい入力を受け付けた後は、旧入力から作ったCollaboration候補の自発配送を終了する。作品版・条件・出所が有効なら通常返答の補足に使える。入力受付と配送確定の順序はサーバーで観測した順に扱う。入力受付が先なら表示せず、配送確定が先なら表示済みとして次の入力を処理する。 [Agencyの待機判定](../../eumenes/api/application/agency/always-on-host.ts#L135-L143)
2. **先に確定した一件を出す。** 会話が空いていれば、同じwriterで最初に有効性を確認できた一件を優先する。対象会話・設定・直近の入力・配送済み記録と、各機能が持つ候補の世代・期限・根拠を確認し、会話への追記またはLiveへの引き渡し受付と配送記録を同じトランザクションで確定する。配送記録には、確定時点のAgencyの発話間隔から計算した、別の提案元が配送できる最も早い時刻を残す。Fでは既存の送信間隔、always-onでは本体が正規化した発話間隔を使う。他方はその時刻を過ぎ、会話が空いてから再照合する。同じ提案元には各機能の間隔と上限を適用する。保存が失敗した場合は配送記録も戻し、他方は次の判定で配送できる。 [Fの送信間隔](../../eumenes/api/application/agency/delivery.ts#L117-L132) · [always-onの間隔設定](../../eumenes/api/application/agency/always-on-scope.ts#L50-L55)
3. **後着の候補を扱う。** Collaborationは候補を保留し、初回比較では起点のターン確定から30秒を自発提案の締切とする。締切後は、作品・条件・出所が有効な候補だけ通常返答の補足に回す。たとえばFの発話が先に確定し、発話間隔の満了が締切より後なら、そのCollaboration候補は自発配送を終了する。always-onは有効なチケットを保留し、発話間隔の満了と会話の空きを待つ。Fは既存の間隔超過と同じ中断結果で当該チケットを閉じ、次の既存の機会に判断する。保留の再判定では切替・停止・入力の更新、根拠と期限を再照合する。再判定は会話が空く通知や間隔の満了を使い、待機中の再推論は行わない。 [Fの中断結果](../../eumenes/api/application/agency/delivery.ts#L154-L166) · [always-onの待機処理](../../eumenes/api/application/agency/always-on-cycle.ts#L225-L249)
4. **一度出した候補を消費する。** 同じCollaboration候補を通常返答の補足に添えた場合も、自発配送と同じ候補IDで消費する。再起動や重複受付では確定済みの配送記録を照合する。Liveへの引き渡し受付と実際の再生は別に記録する。Collaborationの自発提案はテキストで保存し、次の通常ターンに候補IDと文面を参照として渡す。参照は表示済みの有効な提案に限り、記憶への自動取り込みは抑止する。 [Liveと会話保存の分岐](../../eumenes/api/application/agency/speech.ts#L20-L75) · [会話経過の組み立て](../../eumenes/api/domains/dialogue/service/specialist-memory.ts#L36-L116)

## 4. 比較課題と採否基準

### 正式比較の登録

- **課題と反復。** 開発用6件で候補・指示・採点表を調整する。評価用24件は「次工程の準備が役立つ」「阻害要因がある」「待つのが妥当」「提案不要」を各6件とし、同じ課題を各構成2反復する。A・A+・B・Cで最大192対話。評価結果を見て調整した場合は、調整に使った課題を外し、未使用の評価課題で比較を登録し直す。 [課題の分割](../eval/proactive/README.md#課題と採点)
- **比較条件。** 先回り支援専用の `eval/proactive/protocol.json` を基に、対象コミット・配布物と課題のハッシュ、モデル・推論設定・実際の前景と背景の経路、Agencyのモードと間隔、利用者役と採点表、観測時間、呼出し数・費用の上限を一つの登録に記録する。比較する構成で共通の条件を使い、経路・モデル・観測方法が変わった場合は比較相手も揃えて採り直す。予算切れ・タイムアウト・未完了は分母に残す。 [先回り支援のprotocol草案](../eval/proactive/protocol.json)
- **基準測定。** 保管済みのAの48試行は、通常返答と作品・条件の予備記録として使う。当時の収集は待機中の単独通知を数えていない。正式比較のAは、下記の観測方法で同じ条件のB・Cと比較できるよう採り直す。 [Aの測定条件と結果](../eval/results/2026-11-11/proactive-mode-a/README.md#測定条件)

### 利用者に届いた提案の観測

1. 作品と条件が更新された通常返答の確定から、全構成で同じ30秒の観測枠を取る。既存の会話記録から通常返答と待機中に単独で追加されたメッセージを順に取得し、利用者役には判断時点までに受け取った文面を渡す。枠の終わりに、課題に必要な材料が足りない場合だけ既定の追加発言を一度送る。通常返答で後から使われた補足や、枠の後に誤って届いた自発提案も、試行終了まで別に記録する。
2. 各候補について、提案元、作品版、候補の生成時刻、配送判断と保留・失効理由、実際の文面、会話のメッセージIDと表示順、配送時刻、利用者の判断・追加指示・手戻りを対応づける。会話に保存されたテキストを表示の記録と照合する。Liveでの受付は再生の確認と区別する。配送の証拠がなければ、利用者に届いた件数に含めない。
3. 採点者には構成名を伏せ、課題ごとの判断材料と、利用者が受け取った文面・時刻・後続の行動を渡す。次に取れる具体的な一手とその根拠があり、実際に判断する前に届いたかを採点する。生成だけ、既に頼まれた作業の進捗通知だけ、判断後の到着は早期提案の成功に含めない。開発用の固定試験では通常ターンの外からテキストを一件届け、利用者役・採点・集計が同じメッセージと時刻を参照することを確認する。

### 採否

| 判定 | 条件 |
| --- | --- |
| 候補を接続する（工程1→2） | 開発用の先読み・阻害要因の両方で根拠付き候補を確認する。待つべき例では妥当な保留を確認し、架空の根拠は固定試験で全件拒否する。独立した複数の開発用課題で、通常ターンの入力だけでは得られない確認を候補が含む。 |
| 本体へ配線する（工程2→3） | 工程1の候補が、同じ課題でのA+の補足にない根拠または確認結果を、少なくとも3つの独立した開発用課題で含む。満たさず、A+がAより改善する場合は、補足欄だけの採否を判断する。A+にも改善がなければ、開発用課題で準備対象を見直す。 |
| A+を単独で採用する | Aと比べ、準備・阻害要因の課題で改善した件数が悪化した件数を上回り、主指標と条件充足を維持する。待つべき課題と提案不要の課題では、どの反復にも悪化がないことを確認する。 |
| Bを採用する | Aと比べ、少なくとも3つの独立した課題で、条件の言い直し・次の作業指示・手戻りのいずれかが減る。A+と比べても、少なくとも2つの独立した課題で同じ改善があり、改善した課題数が悪化した課題数を上回る。改善は「次工程の準備が役立つ」「阻害要因がある」の12課題で数え、残りの12課題ではどの反復にも悪化がないことを確認する。A・A+それぞれに対し主指標と条件充足を維持する。重大な退行があれば見送る。 |
| Cを採用する | Bと比べ、少なくとも2つの独立した課題で、早く伝えたことが追加指示または手戻りの回避につながる。提案が判断前に届き、その内容を利用したことを記録で確認する。主指標と条件充足を維持する。割り込み・失効済みの提示・二重配送は固定試験で0件、不要な自発提案は評価用24件で0件とする。 |
| 費用と待ち時間 | モード別に背景推論数、費用、準備の実利用率、前景応答の中央値とp95を記録する。初回は既存の草案とAの登録に沿って、前景p95の増加をA比10%以内かつ1,000 ms以内とする。同じ計測区間を用い、タイムアウトの件数と遅い事例も併記する。 |

主指標は「合意条件を満たし、ユーザーが既出条件や次の作業を指示し直さず、割り込み等の違反なく完成した試行の割合」。同じ課題・反復番号を一組とする。候補側が完成し合意条件を満たし、追加指示か手戻りの少なくとも一方が減り、他方が増えなければ、その組は改善とする。完成・条件充足・追加指示・手戻りのいずれかが悪化した組は悪化とする。2組のうち一組以上が改善し、もう一組に悪化がなければ「改善1課題」と数える。悪化があり改善がなければ「悪化1課題」、改善と悪化が両方あれば揺れとして別に示す。比較相手の反復で主指標の成否が分かれた課題は、候補側の両反復が主指標を満たした場合に限り改善に数える。

人の通し試験では、開発用の各群から一課題ずつ選び、A+とA、BとA+、CとBをそれぞれ同じ初期状態で比較する。課題ごとに実施順を入れ替え、どの提案を使って次に進んだか、不要な介入や手戻りがあったかを記録する。固定課題の条件を満たし、通し試験でも想定した使われ方が観測でき、作業を妨げる提案がなければ採用する。効果が確認できなければ採否を保留し、作業を妨げた場合は当該構成を見送る。実施条件と採点表は採取前に登録する。

## 5. 検証、切戻し、完了条件

1. **部分試験。** 条件の空更新、根拠の改変・忘却、対象版の変更、提案の重複、出力形式、費用・期限、再起動時に結果が不明な推論を固定応答で検証する。モードAの出力契約と出力スキーマが現行と一致すること、背景用読出しが状態を書き込まないことも確認する。Collaboration側は `bun run eval:check` と新しい評価・再集計の固定試験、共有コードを変更した場合は `bun run verify` を通す。
2. **結合試験。** 隔離DBと既存Queueを使い、終了時の登録とwriterのロールバック、登録に失敗しても通常ターンが確定すること、新しい入力が来る競合、候補の選択から表示までに生じた手編集、通常返答と自発配送の同時到着、入力中、別作品への切替、F・always-on双方との競合を試す。背景推論が通常ターンと同じ経路で受け付けられること、返答が外部出力へ渡る場合に補足が付かないこと、配送後の通常ターンで提案の文面を参照できることも確かめる。Eumenes側は `bun run verify -- --domain dialogue` と `--domain ui-compositions` を実施し、Queue・Inference・Agencyの共用経路を変更した場合は該当domainも実行する。接続の回帰は `bun test ./api/application/toolchain/specialist-dialogue.test.ts` を含め、対象ファイルを明示する。 [本体の検証手順](../../eumenes/docs/toolchain-extension-verification.md)
3. **通し試験。** `bunx playwright test tests/browser/ui-compositions.spec.ts` と、隔離したUI制作での実モデル比較を別々に記録する。作成、準備、条件一件の訂正、旧候補の失効、最新版の提案のテキスト表示、見送り、通常編集の継続まで通す。試験の観測記録と画面で見えた文面・順序を照合する。固定試験の失敗は原因を解消してから次の段階に進み、比較の途中で課題・閾値を変えない。既存の失敗が見つかった場合は基準版で照合し、成功した範囲を記録する。
4. **切戻し。** 新規セッションの既定をAに戻し、ホストの試験用有効化設定で、進行中も新規起動・補足・自発配送を止める。設定は起動時と配送確定時に照合し、停止前の未配送候補は失効させる。作品・条件・通常の会話は既存の保存経路で継続する。Agencyは既存の発話判断と間隔で動く。Cだけ見送る場合は自発配送を止めてBを使い、背景準備を見送る場合はA+の採否に従う。

自発配送の競合は、Fとalways-onで同じケースを実行する。固定時刻と保存直前の待機点で順序を作り、会話記録と配送記録を照合する。

| ケース | 成功条件 |
| --- | --- |
| Agencyが先、Collaborationが先の両順序 | 先の一件だけが確定する。後着のCollaborationとalways-onは保留し、後着のFは当該チケットを中断する。保留の再判定は間隔の満了後に行う。別会話の配送に影響しない。 |
| AgencyがLiveへ引き渡し、読み上げが継続 | 引き渡しを配送記録に残し、再生中の自発表示は0件。実際の再生を別に確認できる。 |
| 保留中に入力、訂正、忘却、作業切替、期限切れ | 入力受付が先なら自発表示は0件。入力か締切で自発配送を閉じた場合、有効な候補だけ通常返答へ回せる。出所や版が失効した候補は補足にも出ない。 |
| 通常返答への補足と自発配送が競合 | 同じ候補は一方の経路で一度だけ表示され、両経路から会話に出ない。通常返答の保存は完了する。 |
| 保存失敗、重複受付、再起動 | 保存失敗で他方が塞がれず、再起動や重複受付で配送済みの一件を再送しない。保留の再判定は確定済みの間隔と現時点の有効性に従う。 |
| 試験用の機能を停止 | 進行中のCollaboration候補も提示0件。通常会話とAgencyの発話が既存経路で継続する。 |

背景準備・補足欄・自発提案の検討を再開した場合は、比較結果と各段階の採否、主要な失敗例、切戻しの確認を記録する。Evaluatorの指摘、Pursuitへの長時間委譲、他の制作経路は、再開時の比較で見つかった不足に応じて検討する。

## 6. 着手前に固定する実装・試験条件

- **工程0。** §4の正式比較の登録を保存する。実行コード、モデル設定、呼出し・費用の予算、利用者役、観測の固定試験、採点表、人の通し試験に使う課題を記録する。
- **工程2・3。** モードと停止設定の保存先、補足の表示位置・文字数・読み上げ、候補の保存項目を現行ホストに照らして決める。
- **工程5。** F、always-on、Collaborationそれぞれの配送確定点を固定し、共通の記録を既存の会話保存経路のどこに持つかを決める。§5の競合ケースを満たすことを固定試験で確認してから、Cの正式比較を行う。
