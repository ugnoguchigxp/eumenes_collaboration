# Eumenes Collaborationの先回り支援 実装計画

2026年11月11日 · 実装前の計画案

[先回り支援の方針](proactive-collaboration-plan-2026-11-11.md) に基づき、`ui.compose` の `ui.studio@5` で、次の制作判断に必要な材料を一件先に用意する。候補の質、補足欄だけの効果、背景で準備する効果、自発提案の効果を、費用の小さい順に確かめる。製品コードはEumenes本体の既存のDialogue、UI制作、Queue、Inferenceに接続する。Collaborationリポジトリでは比較課題、採点方法、結果の再集計と、工程2・4で追加する返答の出力契約を管理する。将来はEvaluatorの指摘も、同じ固定入力へ根拠として追加できる。 [対象binding](../../eumenes/api/domains/capabilities/bundles/ui-compositions.bundle.json#L145-L175)

本体への行番号つきの参照は、Eumenes `4ed26d7f` に未コミットの変更が載った作業ツリーで照合した。比較に使う基準コミットは工程0で記録する。

## 1. 最初の対象と実行モード

最初の起点は、成功したUI共同制作の通常ターンの終了時とする。対象は `reply` で確定したターンに限り、ホスト観測のターンと、担当を離れる `return`・`discard` は起点にしない。作品の定義または確定条件に実質的な更新があり、作品が存在する場合に計画を一度起動する。たとえば一覧画面を整えたところで、合意済みの「公開前に確認する」という条件から、次に必要になりそうな確認画面の選択肢を、既存の画面定義と検査結果に沿って整理する。

準備の対象は、通常ターンが同じ入力と推論回数では行えない確認から選ぶ。通常ターンと同じ材料を読み直すだけの準備は、背景処理を作る理由にならない。第一候補は、確定済みの条件を一件ずつ定義の全文と照合する確認とする。通常ターンには大きな定義が概要として渡される場合があり、返答も二文・300字に収める必要がある。どの確認を採るかは工程1の採点で決める。背景処理は読み取りだけで完結し、作品を占有しない。計画中も通常ターンと画面からの編集を受け付け、版の照合で古い結果を失効させる。UIからの手編集やUndoは初回から失効判定に使い、単独で計画を起動する範囲は後続の比較で判断する。 [通常ターンへの文書の渡し方](../../eumenes/api/domains/dialogue/service/specialist-memory.ts#L145-L157)

隔離した試験ホストで以下を切り替える。既定はA。モードはセッションの開始時に決めてセッションと各記録に残し、途中では切り替えない。候補だけを採点する段階では、試験用の記録に限定する。モデルと接続先は既存設定から取得し、比較中は同じ経路を固定する。

| モード | 挙動 |
| --- | --- |
| A 現行 | 現在の共同制作をそのまま実行する。出力契約と推論入力は現行と一致させる。 |
| A+ 補足欄のみ | 背景処理を使わない対照。通常のモデルが同じ呼出しの中で、次に必要な判断を補足欄に書く。表示と文字数の上限はBと同じにする。 |
| B 準備 | 背景で用意した有効な準備結果を、次の通常の返答で補足として使う。 |
| C 準備と自発提案 | Bに加え、次の返答まで待つと判断が間に合わない候補を、空いた時点で一件だけテキスト表示する。 |

A+を置くのは、BがAに勝った理由を見分けるためである。Bは、返答の枠の外に補足を出せることと、推論を一回多く使えることの両方でAより有利になる。A+で前者を揃え、背景での準備と検査に固有の効果だけをBとの差として測る。

## 2. 実装箇所と順序

本体への配線は、候補の質と補足欄の効果を確かめた後に行う。各工程は、次へ進む条件を満たした場合だけ次に進む。

| 工程 | 変更する箇所 | 実装と引き渡し条件 |
| --- | --- | --- |
| 0. 比較基準の固定 | Collaborationの `eval/` | 既存の課題検査・保管・再集計を起点に、制作の経過と提案してよい時間帯を表現する課題を追加する。既存の課題は固定した発話列をexample hostで再生する形式で、指示の言い直しや空き時間、各モードの挙動を表現できない。隔離したEumenesホストで対話を進める実行経路と、構成間で共通にする利用者役（反応の規則またはLLM、そのモデルと判断条件）を先に決める。調整用と評価用を分け、モデル、入力、許容値、予算、Eumenesの基準コミット、同梱しているCollaborationパッケージのdigestを記録する。モードAを採取し、各ターン終了時の定義・条件・出所を工程1の固定入力として保存する。 [既存の評価契約](../eval/README.md) · [既存の実行経路](../eval/live-v2.ts#L1-L27) |
| 1. 候補の質をオフラインで確認 | Collaborationの `eval/` | 工程0で保存した固定入力から、評価ハーネス上で実モデルに候補・保留を生成させる。本体のコードは変更しない。人が構成を伏せて、根拠の正しさ、時期、範囲、通常ターンの入力だけでは得られない確認を含むかを採点する。準備の対象を複数試し、採る確認を一つに決める。進む条件は§4の「候補を接続する」。満たさなければ入力と判断基準を見直し、本体には配線しない。 |
| 2. 補足欄と対照A+ | Collaborationの出力契約、Dialogueの出力確定 | 返答の本文とは別に表示する補足欄を追加する。現行の契約は未知の欄を拒否するため、状態更新つき契約と同じopt-inの契約としてCollaboration側に追加し、Eumenesの同梱パッケージを更新する。モードA+を採取してAと比べる。工程1の候補と、同じ課題でのA+の補足を人が比べ、候補にしかない根拠や確認結果があるかを記録する。 [現行の出力契約](../src/agent/action.ts#L26-L44) · [opt-inの契約](../src/agent/stateful-turn.ts#L7-L40) · [回答の保存](../../eumenes/api/domains/dialogue/service/specialist-settle.ts#L189-L201) |
| 3. 固定入力と候補の生成 | EumenesのDialogue、UI制作adapter、Inference | Dialogueに、既存の出所検査を共用する読み取り操作を置く。UIの文書読出しと定義検査を再利用する。通常ターンを確定する `settleSpecialistTurn` の中で、実質変更があれば最新の入力を同じwriterでQueueへ登録する。登録できない場合（容量超過など）は起動を見送り、通常ターンの確定は巻き戻さない。既存の背景推論（`captureBackgroundControlInTransaction`）で構造化された候補を生成する。経路は `route: "conversation"` を明示する。省略するとローカル限定の経路になり、通常ターンと条件が揃わない。締切と出力量は構造化出力の既存上限（300秒、2400トークン）の範囲で決める。試験用の記録で、工程1と同等の候補が本体の経路でも得られることを確かめる。 [ターンの確定](../../eumenes/api/domains/dialogue/service/specialist-settle.ts#L132-L201) · [UIの定義読出しと検査](../../eumenes/api/application/media/ui-compositions-adapter.ts#L311-L346) · [背景推論](../../eumenes/api/domains/inference/service/background-control.ts#L72-L145) |
| 4. 準備結果を通常返答へ | Collaborationの出力契約、Dialogueの通常ターンと出力確定 | 固定した資料の確認結果を候補として保持する。試験用の出力契約に候補IDの選択欄を追加し、関連性の判断は通常のLLM呼出しで行う。選ばれた補足を、出力確定時に有効な場合だけ工程2の補足欄に表示する。通常ターンの推論回数を維持し、BをAとA+の両方と比較する。 [推論入力](../../eumenes/api/domains/dialogue/service/specialist-turn.ts#L433-L476) |
| 5. 自発提案の配送 | Dialogueの会話配送と本体のAgency接続 | Bの採用が決まってから設計と実装に着手する。先に知らせる候補を、会話が空いた時点で同じ会話にテキスト表示する。既存の入力中・前景推論・読み上げの状態を利用し、Agencyの自発発話と同時に出ないよう本体のwriterで配送を調停する。配送した文面は次の通常ターンの入力へ渡す。候補が選ばれたこととメッセージが保存されたことを別に記録し、BとCを比較する。 [Agencyの待機判定](../../eumenes/api/application/agency/always-on-host.ts#L100-L119) · [既存の発話配送](../../eumenes/api/application/agency/always-on-flow.ts#L145-L189) |

方針文書の段階との対応は、工程0が段階0、工程1と3が段階1、工程2と4が段階2、工程5が段階3である。

工程3の背景用読出しでは、既存の `collaborationSnapshot` のうち検証だけを共用する。この関数は通常ターンの `runId` を使って出所を登録し、失効も保存するため、背景処理の入口としてそのまま呼び出すと状態の書込みを伴う。読み取りで無効な出所が見つかった場合は、保存せずに、その出所に依存する条件を除いた状態を入力にする。編集済み・忘却済みの原文は背景推論へ渡さず、失効の保存は次の通常ターンに任せる。文書本文は現行の正規化済み定義を使い、必要なら現行validatorを読み取りで実行する。作品の画面表示や動作については、実際に確認した材料がある範囲を記録する。 [現行の条件取得と登録](../../eumenes/api/domains/dialogue/service/collaboration-state.ts#L26-L160) · [正規化されたUI文書](../../eumenes/api/domains/ui-compositions/service/work.ts#L114-L125)

## 3. 入出力と採用条件

| データ | 最小の項目と扱い |
| --- | --- |
| 固定入力 | `sessionId`、`epoch`、binding版、作品ID・版・digest、条件・出所の版、提示資料のID・位置、直近の制作目的と確定済みの条件、関連する過去候補。入力の範囲と実際に提示した出所をホストが記録する。 |
| 候補 | ホスト発行ID、保留・準備・提案の選択、次に必要な判断、根拠の参照、観測と仮説、推奨する次の一手、早めに伝える理由、未確認点。LLMが根拠の意味と関連性を判断し、ホストがID、参照位置、サイズ、利用可能な操作を検査する。 |
| 実行と結果 | 入力識別子、実行世代、モード、Queueジョブと推論の受付・結果、候補または終了理由、期限。結果は `保留`、`有効`、`失効`、`中断`、`失敗` を区別する。準備済みと配送済みは別に記録する。 |
| 提示と反応 | 候補ID、配送先会話、応答のメッセージID、提示経路、利用者の見送り・却下・訂正・停止。モデルが反応の意味と候補の対応を読み、ホストが実在する利用者発言・対象候補・会話を照合する。 |

新しく設ける保存先のテーブルと欄、出力契約の欄名は、工程2・3の着手前にこの文書へ書き足す。名前を決めずに着手しない。

- **起動と競合。** Queueにセッション単位の同時実行キーを付け、同じ入力は一度だけ受け付ける。重複防止のキーは入力識別子から作る。同じキーで内容の違う登録は既存Queueが拒否するため、payloadは入力識別子に限る。ジョブは背景レーンに置く。計画中に入力が変わったら、旧結果を失効させ、実行が落ち着いた時点で最新の入力だけを計画する。ジョブは開始時に自分の入力がセッションの最新かを照合し、古ければ推論せずに失効で閉じる。起点は作品と条件の実質変更。状態版は追跡用に残し、空更新や新しい出所の登録だけで不要な計画を起こさない。初期値は、一入力につき背景推論一回、保持する候補一件。締切・入出力上限・費用は工程0で固定する。 [既存Queueへの登録](../../eumenes/api/domains/queue/service/index.ts#L65-L105) · [状態版の更新](../src/agent/state.ts#L149-L155)
- **保存の所有者。** Dialogueがセッション単位の最新入力と有効候補を所有する。製品接続で永続化する際はDialogueの既存migration経路を使う。Queueには識別子だけを渡し、候補本文や出所の原文を複製しない。却下・配送の記録には照合に必要な範囲を残し、期限切れや忘却を既存のライフサイクルに接続する。明示的な停止は対象会話・セッションに保存し、再開まで自発配送を抑える。
- **保存と再確認。** 結果採用時と表示直前に、セッションが有効であること、セッション世代・binding・作品版を再検査し、実際に提示した条件の値・状態・出所の有効性を照合する。出所台帳の版が変わった場合は、提示した参照の中身を再照合する。実質変更を見分ける比較は正規化した構造に対して行う。意図や提案の意味は文字列の重なりで判定せず、モデルに既出候補と根拠を渡す。忘却時は依存候補の本文と参照を既存の忘却トランザクションで削除する。発行済みの推論結果が再起動後に不明なら中断として閉じる。 [条件の忘却処理](../../eumenes/api/domains/dialogue/service/collaboration-state.ts#L255-L293)
- **補足欄。** 返答の `text` は読み上げを前提に二文・300字までに制限されている。補足はこの枠に含めず、文字数の上限を別に定めたテキスト表示とし、読み上げの対象にするかは工程2の着手前に決める。A+とBで表示と上限を同じにする。返答が外部出力へ引き渡され、会話にメッセージが残らない場合は補足を添えない。Bではその候補を未消費のまま残す。 [返答の制限](../../eumenes/api/domains/delivery/service/speech-reply.ts#L3-L4) · [回答の保存経路](../../eumenes/api/domains/dialogue/service/specialist-settle.ts#L44-L60)
- **通常返答の保護。** モードBでは、通常のモデルに候補IDと対象・用途の短い見出しを渡す。結論や提案文は、出力確定時にホストが補足欄に表示する。通常本文や操作に未検証の準備内容が混ざると、作品を編集したあとに古くなった情報だけを取り除けないためである。補足を選んでも、同じターンで作品や関連条件が変われば、本文を保存し補足を落とす。候補IDで付与するのは表示の選択だけで、操作の権限には使わない。
- **自発配送の保護。** モードCでは、計画時より新しいユーザー入力があれば、自発配送は保留し通常返答での利用を優先する。候補の有効性、入力・前景処理・読み上げ・停止、同じ候補の配送済み状態を最後に確認する。入力中と読み上げはプロセス内の状態なので書込みの直前に確認し、DBで照合できる条件は同じトランザクションで再確認する。通常返答で添えられた場合も同じ候補IDで消費する。会話への追記と配送記録は単一writerで確定し、同じ候補IDを再配送しない。現行のホスト観測ターンは仕事の占有と追加推論を伴うため、この段階では、確定済みテキストを既存の会話保存へ渡す方式を第一候補とする。保存時は通常の回答と同じく、記憶への取り込みの抑止と会話イベントの記録を行う。現行の会話経過（`sessionCourse`）はrunの入力と回答から組み立てるため、runを持たない自発提案は次の通常ターンの入力に現れない。配送済みの候補IDと文面を次の通常ターンの参照情報に含め、利用者の反応をモデルが候補と対応づけられるようにする。補足を別のメッセージとして保存する場合も同じ経路で渡す。Agencyの `claimAgencyDispatch` はAgencyの保存状態に依存するので、調停を共用する際は会話単位の配送契約を本体で設計し、Fとalways-onの既存挙動を回帰試験する。 [ホスト観測の受付](../../eumenes/api/domains/dialogue/service/specialist-notices.ts#L87-L144) · [会話経過の組み立て](../../eumenes/api/domains/dialogue/service/specialist-memory.ts#L36-L116) · [Agencyの配送間隔](../../eumenes/api/domains/dialogue/repository/agency.ts#L31-L46)

## 4. 比較課題と暫定の採否基準

調整用6件と評価用24件を分け、評価用は「次工程の準備が役立つ」「阻害要因がある」「待つのが妥当」「提案不要」を各6件にする。題材と言い回しを変え、別作品への切替、訂正、既出提案の却下を含める。まずは各構成2反復の案とし、構成ごとに48対話、4構成で最大192対話。構成は工程の順に採取する。途中で経路のモデルが更新された場合は、比較相手の構成を採り直す。protocol v3はdraftで、反復3対3と `cross_provider_session` を主指標に置いている。今回の2反復・単一経路の案と食い違うため、どちらに揃えるかを決めてから登録する。工程0で必要推論数と費用を見積もり、実行可能な反復数、モデル、課題の版、採点表を固定する。利用者役は構成間で同じ規則・モデル・判断条件を使う。調整用の結果は最終判定から除く。採点は構成名を伏せ、人が根拠・時間帯・手戻りを確認する。 [protocol v3](../eval/protocol-v3.json)

| 判定 | 初期案 |
| --- | --- |
| 候補を接続する（工程1→2） | 先読み・阻害要因の両方で根拠付き候補を確認する。正常例では妥当な保留を確認し、架空の根拠は固定試験で全件拒否する。独立した複数の課題で、通常ターンの入力だけでは得られない確認を候補が含む。 |
| 本体へ配線する（工程2→3） | 工程1の候補が、同じ課題でのA+の補足にない根拠または確認結果を、少なくとも3つの独立した課題で含む。満たさず、A+がAより改善する場合は、補足欄だけを採用して背景準備を見送る。A+にも改善がなければ、準備の対象と課題を見直す。 |
| Bを採用する | Aと比べ、少なくとも3つの独立した課題で、条件の言い直し・次の作業指示・手戻りのいずれかが減る。A+と比べても、少なくとも2つの独立した課題で同じ改善があり、改善した課題数が悪化した課題数を上回る。改善は「次工程の準備が役立つ」「阻害要因がある」の12課題で数え、残りの12課題では悪化がないことを確認する。主指標を維持する。条件充足の低下や重大な退行があれば見送る。BがA+を上回らない場合は補足欄だけを採用する。 |
| Cを採用する | Bと比べ、少なくとも2つの独立した課題で、早く伝えたことが手戻りの回避につながる。主指標と条件充足を維持する。固定試験で割り込み禁止・失効・二重配送の違反は0件。意味評価では、提案不要の6課題に自発提案が出ないことを目標とし、「待つのが妥当」の課題を含めた不要な自発提案の上限を工程0で数値として確定する。 |
| 費用と待ち時間 | モード別に背景推論数、費用、準備の実利用率、前景応答の中央値とp95を記録する。前景p95の悪化は現行比10%以内を暫定案とし、試行前に絶対時間の上限も決める。A+は出力が増える分の遅延を同じ基準で測る。短い標本では分布と遅い事例を併記する。 |

主指標は「合意条件を満たし、ユーザーが既出条件や次の作業を指示し直さずに完成した課題の割合」。課題別と全試行を併記し、改善した課題数は同じ課題の反復をまとめて判定する。2反復では同じ構成でも結果が揺れるため、工程0でモードAの反復間の差を測り、その差を超えた課題だけを改善・悪化に数える。

固定課題の主指標は利用者役の作り方に左右される。このため、採否は人の通し試験と合わせて決める。A+・B・Cそれぞれの採取後に、隔離環境で人が同じ制作課題を各構成で行い、補足や提案の採用・見送り、指示の言い直し、邪魔になった場面を記録する。固定課題で改善が出ても、通し試験で補足が使われない、または作業の妨げになる場合は採用を見送る。件数と記録項目は工程0で確定する。閾値と試行規模は採取前に確定する提案値である。

## 5. 検証、切戻し、完了条件

1. **部分試験。** 条件の空更新、根拠の改変・忘却、対象版の変更、提案の重複、出力形式、費用・期限、再起動時に結果が不明な推論を固定応答で検証する。モードAの出力契約と出力スキーマが現行と一致すること、背景用読出しが状態を書き込まないことも確認する。Collaboration側は `bun run eval:check` と新しい評価・再集計の固定試験、共有コードを変更した場合は `bun run verify` を通す。
2. **結合試験。** 隔離DBと既存Queueを使い、終了時の登録とwriterのロールバック、登録に失敗しても通常ターンが確定すること、新しい入力が来る競合、候補の選択から表示までに生じた手編集、通常返答と自発配送の同時到着、入力中、別作品への切替、F・always-on双方との競合を試す。背景推論が通常ターンと同じ経路で受け付けられること、返答が外部出力へ渡る場合に補足が付かないこと、配送後の通常ターンで提案の文面を参照できることも確かめる。Eumenes側は `bun run verify -- --domain dialogue` と `--domain ui-compositions` を実施し、Queue・Inference・Agencyの共用経路を変更した場合は該当domainも実行する。接続の回帰は `bun test ./api/application/toolchain/specialist-dialogue.test.ts` を含め、対象ファイルを明示する。 [本体の検証手順](../../eumenes/docs/toolchain-extension-verification.md)
3. **通し試験。** `bunx playwright test tests/browser/ui-compositions.spec.ts` と、隔離したUI制作での実モデル比較を別々に記録する。作成、準備、条件一件の訂正、旧候補の失効、最新の準備の利用、見送り、通常編集の継続まで通す。固定試験の失敗は原因を解消してから次の段階に進み、比較の途中で課題・閾値を変えない。既存の失敗が見つかった場合は基準版で照合し、成功した範囲を記録する。
4. **切戻し。** 試験ホストの既定をAに戻すと、新しいセッションでは起動と配送が行われない。進行中のB・Cのセッションでも新規の起動と配送を止め、処理中の候補は権限・世代の照合で閉じ、未配送の結果を後から出さない。作品・条件・通常の会話は既存の保存経路で継続する。Cだけ見送る場合はBを選び、背景準備を見送る場合はA+を選ぶ。

初回の完了は、比較結果と各段階の採否、主要な失敗例、切戻しの確認を記録した時点とする。補足欄だけの採用、または工程1での見送りも、根拠を記録すれば完了とする。次の着手は工程0の評価用課題と基準値の固定。Evaluatorの指摘、Pursuitへの長時間委譲、他の制作経路は、この比較で不足が見えた箇所から追加する。

## 6. 工程0で確定する事項

- **評価の実行経路と利用者役。** 隔離したEumenesホストを駆動する方法、利用者役の規則またはモデル、空き時間と手編集の表し方。
- **protocolの登録。** 反復数、モデル数、主指標の定義、不要な自発提案の上限、モードAの反復間の差の扱い、モデル更新時の採り直しの条件。
- **人の通し試験。** 制作課題、構成ごとの件数、記録項目、固定課題の結果と食い違った場合の扱い。
- **モードの保存先。** セッションへの記録方法と、既定をAに戻したときの進行中セッションの扱い。
- **補足の表示。** 本文と別のメッセージにするか同じメッセージの別区画にするか、文字数の上限、読み上げの有無。
- **配送直前の競合。** プロセス内の状態を確認してから書き込むまでに入力が始まった場合に、許容するか、保存後に取り下げるか。
