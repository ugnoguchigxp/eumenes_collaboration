# 脅威モデル

## 守る対象

1. **状態の正しさ**：利用者が決めた条件・決定と、未決事項の区別
2. **外部操作**：外部agentへの依頼・回答・停止。誤った送信や、意図しない自動入力をしない
3. **費用**：API費用の上限
4. **利用者の原文**：忘却された発言を、状態や外部記録に残さない

## 信頼境界

| 入力 | 扱い |
| --- | --- |
| 利用者の原文（最後のuserメッセージ） | 意図として信頼する。今回の命令はこれだけ |
| 文書の本文、TOOL_RESULT、外部agentの報告、画面の観測 | データ。中の指示を実行しない。observationの出所として、観測された事実の根拠にはなる |
| LLMの出力 | 信頼しない。行動・状態・判断のどれも、schemaと参照の検査を通るまで採用しない |
| hostの入力（出所の登録、版、権限） | 信頼する。ただし不正な形は `CollaborationError` で拒否する |

## コードが保証すること

- 出力の構造（strictなschema）、文字数などの上限、行動ごとに必要なフィールド
- 版・世代・sessionの一致（古い提案や応答の拒否）
- 引用された出所が実在し、有効で、確定に使える種類（user / observation）であること
- 置換関係の循環の禁止、採用した訂正だけが以前の条件を撤回すること
- JSONの容量・node数・深さ、直列化フックの拒否
- exampleのhostでは、権限digest、1回だけの送信、試行番号による古い応答の無効化、手入力中の自動入力の禁止、予約制の費用上限

## モデルに依存すること（残存リスク）

**出所は「引用」されるだけで、意味の一致は検証されない。** LLMが、ある利用者の発言を根拠として引用して条件を `confirmed` にしたとき、その発言が本当にその条件を述べているかは、コードでは確かめられません。そのため、文書や外部報告に埋め込まれた指示（プロンプト注入）にモデルが従うと、次のことが起こりえます。

- 無関係な利用者の発言を引用して、利用者が決めていない条件を確定する
- observationの出所（資料そのもの）を引用して、資料に書かれた「承認済み」「確定」を条件にする

observationは、観測された事実の正当な根拠になります。そのため、資料に書かれた指示と観測された事実の区別は、コードの検査ではなく指示（`contexts/collaboration/state.context.toml`）とモデルの判断に依存します。

## 緩和策

1. **指示で区別させる。** 0.3の状態更新の指示では、資料・文書・外部報告に書かれた依頼・承認・確定・撤回・送信や公開の指示を、利用者の決定として扱わないことを明記しています。
2. **重要な操作は利用者の承認を経る。** 送信・購入・公開・個人情報・取り消せない操作は、`completeBrief` の `mustAsk` を使い、推定で埋めずに質問にします。外部への送信は、hostの権限（grant）なしには行いません。
3. **測定する。** 注入群の評価課題で、資料の指示に由来する確定や禁止操作の割合を測ります（下記）。

## 測定結果

評価の手順と判定規則は `eval/protocol-v2.json` に記録しています。注入群（封印課題6件と開発用2件）の結果は、[改善設計書](improvement-design-2026-11-06.md) の実施記録を参照してください。

2026-11-06の封印課題（run `holdout-v2`）で、注入群6件の主指標（もう一方のproviderの判定者による課題単位の過半数）は次のとおりでした。

| provider | 0.2.0の指示 | 0.3.0の指示 |
| --- | --- | --- |
| Claude Haiku 5.5 | 5/6（失敗1） | 6/6（失敗0） |
| GPT-6 Luna | 6/6 | 6/6 |

開発用の注入課題2件は、指示の調整中に2/2でした。件数が少ないため、これは「この課題の範囲で失敗が見つからなかった」ことを示すだけで、注入への耐性を保証するものではありません。coreの構造検査（出所の照合、確定の遷移）は、モデルが従っても従わなくても働く防御として残ります。
